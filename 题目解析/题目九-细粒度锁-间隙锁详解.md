# 题目九：细粒度锁-间隙锁详解

本文档说明题目九“细粒度锁-间隙锁”的完整实现方式。内容主要为：
题目要求分析、
总体并发控制设计、
GAP 锁数据结构、
区间冲突判断、
执行器加锁入口、
优化器配合、
关键边界处理、
本地验证和平台验证结果。

本题建立在前序题目的能力之上：
1. 题目三已经实现唯一索引，以及 DML 执行时对索引的同步维护和唯一性检查。
2. 题目七已经实现显式事务控制，`Transaction` 的 `write_set_` 可以在 `abort` 中逆序回滚基表记录和索引项。
3. 题目八已经实现表级 SS2PL、wait-die 死锁预防，以及事务结束时统一释放所有锁。
4. 本题需要在题目八的正确性基础上降低锁粒度，让索引范围外的数据仍然可以并发插入或修改。

## 一、题目要求分析

题目八使用表级 `S/X` 锁可以保证冲突可串行化，也可以避免幻读。但表级锁的问题是并发度过低：

```text
T1: select * from gap_lock_test where id > 2 and id < 6;
T2: insert into gap_lock_test values (4, ...);
T3: insert into gap_lock_test values (0, ...);
```

在题目八的表级锁方案中：

```text
T1 select 持有表级 S 锁
T2 insert 需要表级 X 锁，被阻塞
T3 insert 也需要表级 X 锁，也被阻塞
```

但是题目九要求更细粒度的行为：

1. `id=4` 落在查询范围 `(2,6)` 内，必须被 T1 的范围读挡住，否则 T1 第二次范围读会出现幻读。
2. `id=0` 不在查询范围 `(2,6)` 内，不应该被 T1 的范围读挡住，T3 应该可以先插入并提交。
3. T1 的后续 `select *` 能看到 T3 已提交的 `id=0`，但不能看到 T2 仍未提交的 `id=4`。
4. T1 提交后，T2 才能完成插入并提交。

因此本题的核心不是重新实现事务回滚，而是把题目八中的表级读写锁进一步下沉到：

```text
表意向锁 + 索引区间 GAP 锁 + 扫描范围内已有记录行锁
```

同时仍然需要保留题目八已经实现的要求：

1. 所有锁遵守 SS2PL，事务提交或回滚前不主动释放。
2. 锁冲突继续使用 wait-die 策略，不能引入死锁检测线程。
3. wait-die 导致的回滚仍然通过 `TransactionAbortException` 返回精确的 `abort\n`。
4. 除正常等待外，每条 SQL 的执行链路不能引入额外长耗时逻辑。

## 二、总体设计

本次实现采用“有索引走 GAP 锁，无索引保守表锁”的方案。

核心加锁策略如下：

```text
索引 select              -> 表 IS 锁 + GAP S 锁 + 扫描范围内记录 S 锁
索引 update / delete     -> 表 IX 锁 + GAP X 锁 + 扫描范围内记录 X 锁
insert                   -> 表 IX 锁 + 每个新索引 key 的点 GAP X 锁
update 修改索引 key       -> 新索引 key 的点 GAP X 锁
无索引 select            -> 表级 S 锁
无索引 update / delete   -> 表级 X 锁
有索引但无法局部界定范围 -> 第一条索引上的全范围 GAP 锁
commit / abort           -> 事务结束时统一释放所有锁
```

整体执行链路如下：

```text
客户端 SQL
  -> rmdb.cpp 为连接绑定当前事务
  -> analyze / optimizer 生成 Plan
  -> Portal 把 Plan 转成 Executor
  -> ScanExecutor 根据 READ / WRITE 模式申请表意向锁、GAP 锁和行锁
  -> Insert / Update / Delete 对新增 key 或已有记录补锁
  -> LockManager 按区间重叠和 wait-die 决策等待或回滚
  -> DML 正常执行并记录 write_set
  -> commit / abort 时 TransactionManager 释放所有锁
```

为什么使用“点 GAP X 锁 `[key,key]`”保护插入：

1. 当前 RMDB 的索引是唯一索引，插入一个索引 key 时只需要判断这个 key 是否落入其他事务已经锁住的范围。
2. 范围读持有的是逻辑区间，例如 `(2,6)`；插入 `4` 的点区间 `[4,4]` 与其重叠，所以冲突。
3. 插入 `0` 的点区间 `[0,0]` 与 `(2,6)` 不重叠，所以不冲突。
4. 这种设计不依赖 B+ 树当前物理叶子页分布，也不会因为页分裂改变锁语义。

为什么仍保留表级锁路径：

1. 如果表没有索引，系统无法把谓词映射成有序 key 区间。
2. 这种情况下只加行锁会允许其他事务在扫描后插入满足谓词的新记录，仍然有幻读。
3. 因此无索引扫描继续使用表级 `S/X` 锁，保证正确性优先。

10. `planner.cpp`：表上存在索引但没有局部命中谓词时，选择第一条索引做全范围索引扫描。

std::shared_ptr<std::deque<WriteRecord *>> write_set_;

其中：

3. `txn_id_` 和 `start_ts_` 可以表示事务开始顺序。
4. `state_` 用于禁止事务在 `SHRINKING` 阶段继续加锁。

题目八已经让 `commit / abort` 通过 `release_all_locks()` 遍历 `lock_set_` 并调用 `LockManager::unlock()`。因此本题新增的 GAP 锁只要进入同一个 `lock_set_`，事务结束时就可以复用原释放路径。

### 4.2 LockManager 中已有的数据

题目八已经实现：

```text
lock_table_
LockRequestQueue
LockRequest
lock_internal()
unlock()
S / X / IS / IX / SIX 兼容矩阵
wait-die 决策
锁升级处理
条件变量等待和唤醒
```

表锁和行锁都通过：

```cpp
lock_internal(txn, lock_data_id, lock_mode)
```

进入同一套队列逻辑。

本题没有删除这些逻辑，而是在旁边新增 GAP 锁队列：

```text
gap_lock_table_
GapLockRequestQueue
GapLockRequest
lock_gap_internal()
unlock_gap()
```

原因是 GAP 锁不能使用普通 `LockDataId` 完全相等判断冲突。两个区间即使不是同一个 `LockDataId`，也可能因为区间重叠而冲突。

## 五、GAP 锁数据结构

文件：

```text
rmdb/src/transaction/txn_defs.h
```

原来的加锁对象只有表和记录：

```cpp
enum class LockDataType { TABLE = 0, RECORD = 1 };
```

本题扩展为：

```cpp
enum class LockDataType { TABLE = 0, RECORD = 1, GAP = 2 };
```

GAP 锁的 `LockDataId` 保存以下信息：

```text
fd_                 索引文件 fd
gap_lower_key_      区间下界 key
gap_upper_key_      区间上界 key
gap_lower_inf_      下界是否为 -inf
gap_upper_inf_      上界是否为 +inf
gap_lower_closed_   下界是否闭区间
gap_upper_closed_   上界是否闭区间
gap_col_types_      索引列类型
gap_col_lens_       索引列长度
```

这样可以表达三类核心锁对象：

```text
(2,6)       范围查询 id > 2 and id < 6
[4,4]       插入或更新新 key = 4
(-inf,+inf) 全索引范围扫描
```

`operator==` 和 `hash<LockDataId>` 也同步扩展，保证 GAP 锁可以放进事务的 `lock_set_`：

```cpp
std::shared_ptr<std::unordered_set<LockDataId>> lock_set_;
```

这一点很重要：如果 GAP 锁不进入 `lock_set_`，事务提交或回滚时就无法统一释放，等待事务也无法被唤醒。

## 六、区间冲突判断

文件：

```text
rmdb/src/transaction/concurrency/lock_manager.cpp
```

GAP 锁的兼容性分两步判断：

```text
第一步：两个区间是否重叠
第二步：锁模式是否兼容
```

模式兼容规则沿用题目八的 `S/X` 思路：

```text
GAP S 与 GAP S 兼容
GAP S 与 GAP X 冲突
GAP X 与 GAP X 冲突
```

区间重叠需要处理开闭边界：

```text
(2,6) 与 [4,4] 重叠
(2,6) 与 [0,0] 不重叠
(2,6) 与 [6,6] 不重叠
[2,6] 与 [6,6] 重叠
(-inf,+inf) 与任意有限点重叠
```

实现中使用 `compare_gap_key()` 按索引列类型逐列比较 key：

```text
TYPE_INT    -> int 比较
TYPE_FLOAT  -> float 比较
TYPE_STRING -> 固定长度 memcmp 比较
```

重叠判断可以抽象为：

```text
lhs.lower <= rhs.upper
rhs.lower <= lhs.upper
```

当两个边界 key 相等时，只有两个边界都包含该点，才认为在该点重叠。

例如：

```text
lhs = (2,6)
rhs = [6,6]

lhs.upper == rhs.lower == 6
lhs.upper 是开区间
rhs.lower 是闭区间
因此不重叠
```

## 七、GAP 锁的 wait-die 处理

文件：

```text
rmdb/src/transaction/concurrency/lock_manager.cpp
```

普通表锁和行锁在题目八中已经把等待请求也纳入 wait-die 冲突对象。GAP 锁这里做了一个更精确的处理：

```text
GAP 加锁时，只把已经 granted 的冲突 GAP 锁作为当前阻塞源。
```

原因是题面存在这个调度：

```text
T1: select id > 2 and id < 6      持有 GAP S (2,6)
T2: insert id = 4                 等待 GAP X [4,4]
T1: select *                      需要全范围 GAP S (-inf,+inf)
```

如果把 T2 这个等待中的 `[4,4]` 也当作 T1 的冲突对象，T1 在后续 `select *` 时会因为 T2 更老而被 wait-die 回滚。这不符合题面期望。

因此 GAP 锁策略是：

1. 当前事务申请 GAP 锁时，只检查已经授予的冲突 GAP 锁。
2. 如果已授予冲突锁属于更老事务，当前事务回滚。
3. 如果已授予冲突锁都属于更年轻事务，当前事务等待。
4. 等待时条件变量谓词同样只等待已授予冲突锁消失。

这不会破坏 correctness，因为等待中的请求没有修改任何数据；真正能影响可串行化的是已经持有锁并可能读写数据的事务。

## 八、索引范围构造

文件：

```text
rmdb/src/execution/executor_index_scan.h
```

索引扫描需要把 where 条件转换成两个东西：

1. B+ 树扫描用的 `lower Iid / upper Iid`。
2. GAP 锁用的逻辑 key 区间。

本题复用并扩展了原先的 `make_scan_range()` 逻辑，新增：

```text
IndexGapRange scan_range_
build_scan_range_keys()
locate_scan_range()
```

单列索引示例：

```text
id > 2 and id < 6
```

会构造：

```text
lower_key = 2, lower_closed = false
upper_key = 6, upper_closed = false
GAP 区间 = (2,6)
B+ 树 lower = upper_bound(2)
B+ 树 upper = lower_bound(6)
```

等值查询：

```text
id = 4
```

会构造：

```text
GAP 区间 = [4,4]
B+ 树 lower = lower_bound(4)
B+ 树 upper = upper_bound(4)
```

复合索引需要处理后续列的填充值。规则如下：

```text
a >= v -> lower key 使用 v + 后续列最小值
a >  v -> lower key 使用 v + 后续列最大值，并用 upper_bound
a <= v -> upper key 使用 v + 后续列最大值
a <  v -> upper key 使用 v + 后续列最小值，并用 lower_bound
```

如果同一列有多个同方向条件，会选择更紧的边界：

```text
id > 2 and id > 3  -> 使用 id > 3
id < 8 and id < 6  -> 使用 id < 6
```

## 九、执行器加锁入口

### 9.1 索引扫描

文件：

```text
rmdb/src/execution/executor_index_scan.h
```

索引扫描在 `beginTuple()` 中先加表意向锁：

```text
READ  -> lock_IS_on_table
WRITE -> lock_IX_on_table
```

然后根据 `scan_range_` 申请 GAP 锁：

```text
READ  -> lock_shared_on_gap
WRITE -> lock_exclusive_on_gap
```

最后遍历索引范围时，对扫描到的每条已有记录加行锁：

```text
READ  -> lock_shared_on_record
WRITE -> lock_exclusive_on_record
```

注意这里是“扫描范围内已有记录”，不是“最终满足所有 where 条件的记录”。原因是 where 中可能有残余谓词无法由索引区间表达。例如：

```sql
select * from t where id > 2 and id < 6 and score > 90;
```

索引只能界定 `id` 范围。如果某条 `id` 在 `(2,6)` 内但当前 `score <= 90`，它现在不会出现在结果中；但其他事务不能在 T1 未提交前把它更新成 `score > 90`，否则 T1 第二次查询会看到新记录。因此扫描范围内的旧记录都需要行锁保护。

### 9.2 顺序扫描

文件：

```text
rmdb/src/execution/executor_seq_scan.h
```

顺序扫描分两种情况。

如果表没有任何索引：

```text
READ  -> 表级 S 锁
WRITE -> 表级 X 锁
```

如果表有索引但当前扫描没有可局部利用的索引区间，则使用第一条索引的全范围 GAP 锁：

```text
READ  -> 表 IS 锁 + (-inf,+inf) GAP S 锁 + 扫描记录 S 锁
WRITE -> 表 IX 锁 + (-inf,+inf) GAP X 锁 + 扫描记录 X 锁
```

这个设计有两个作用：

1. 保证 `select *` 这类全表读也能防止幻读。
2. 避免题面中 T2 已经等待插入 `id=4` 后，T1 的 `select *` 再去申请表级 S 锁时被表级 IX 锁或等待请求干扰。

### 9.3 插入

文件：

```text
rmdb/src/execution/executor_insert.h
```

插入流程调整为：

```text
构造记录
构造所有索引 key
表无索引：申请表 X 锁
表有索引：申请表 IX 锁
对每个新索引 key 申请点 GAP X 锁 [key,key]
检查唯一索引重复
插入基表记录
追加 INSERT_TUPLE 写集
插入索引项
```

这样题面中的两个插入会得到不同结果：

```text
T1 持有 GAP S (2,6)
T2 insert id=4  -> 申请 GAP X [4,4]，与 (2,6) 重叠，等待
T3 insert id=0  -> 申请 GAP X [0,0]，与 (2,6) 不重叠，立即执行
```

### 9.4 更新

文件：

```text
rmdb/src/execution/executor_update.h
```

更新流程中有两类锁：

1. 修改已有记录前申请行 X 锁。
2. 如果索引 key 发生变化，对新 key 申请点 GAP X 锁。

第二类锁用于防止“从范围外更新进范围内”的幻读。例如：

```text
T1: select * from t where id > 2 and id < 6;
T2: update t set id = 4 where id = 7;
```

如果只锁旧记录 `id=7`，T2 可以把记录更新成 `id=4`，T1 第二次范围查询就会看到新幻影。因此更新索引 key 前必须对新 key `[4,4]` 申请 GAP X 锁。

### 9.5 删除

文件：

```text
rmdb/src/execution/executor_delete.h
```

删除已有记录时：

```text
表无索引：表 X 锁
表有索引：表 IX 锁
每个待删除 rid：行 X 锁
删除索引项
追加 DELETE_TUPLE 写集
删除基表记录
```

删除不会产生新 key，因此不需要对新 key 申请 GAP 锁。

## 十、优化器配合

文件：

```text
rmdb/src/optimizer/planner.cpp
```

原来的 `get_index_cols()` 只在 where 条件命中索引前缀时返回索引。例如：

```sql
select * from t where id > 2;
```

如果 SQL 是：

```sql
select * from t;
```

原来会走 `SeqScan`。但题面期望中，建有 `id` 索引后 `select *` 的输出顺序是：

```text
0,1,3,5,7,9
```

也就是按索引 key 顺序输出，而不是按基表插入顺序输出。

因此本题新增规则：

```text
如果没有局部命中条件，但表上存在索引，则选择第一条索引做全范围索引扫描。
```

这样有索引的 `select *` 会走：

```text
IndexScan + (-inf,+inf) GAP S 锁
```

既满足题面输出顺序，也统一了全范围 GAP 锁的并发控制路径。

## 十一、关键边界

### 11.1 范围内插入

```text
T1: select id > 2 and id < 6
T2: insert id = 4
```

T1 持有：

```text
GAP S (2,6)
```

T2 申请：

```text
GAP X [4,4]
```

两个区间重叠，且 `S/X` 冲突，因此 T2 必须等待或按 wait-die 回滚。

### 11.2 范围外插入

```text
T1: select id > 2 and id < 6
T3: insert id = 0
```

T3 申请：

```text
GAP X [0,0]
```

`[0,0]` 与 `(2,6)` 不重叠，因此 T3 可以直接执行并提交。

### 11.3 开区间边界

```text
T1: select id > 2 and id < 6
T2: insert id = 6
```

T1 的 GAP 锁是：

```text
(2,6)
```

`[6,6]` 与 `(2,6)` 只在边界 key 相等，但 T1 的上界是开区间，所以不重叠。`id=6` 插入不应该等待。

### 11.4 闭区间边界

```text
T1: select id >= 2 and id <= 6
T2: insert id = 6
```

T1 的 GAP 锁是：

```text
[2,6]
```

`[6,6]` 与 `[2,6]` 在 key `6` 上重叠，所以 T2 必须等待或回滚。

### 11.5 从范围外更新进范围内

```text
T1: select id > 2 and id < 6
T2: update t set id = 4 where id = 7
```

T2 修改索引 key 前会申请：

```text
GAP X [4,4]
```

该点区间与 T1 的 `(2,6)` 重叠，因此 T2 会等待。这样 T1 的重复范围读不会看到由更新产生的新幻影。

### 11.6 残余谓词

```text
T1: select * from t where id > 2 and id < 6 and score > 90
T2: update t set score = 95 where id = 3
```

即使 `id=3` 当前 `score <= 90`，它仍在索引扫描区间 `(2,6)` 内。T1 扫描到该记录时会加行 S 锁，因此 T2 不能把它更新成满足残余谓词的记录。

## 十三、实现效果总结

本题完成后，系统的并发控制粒度从题目八的“整表读写互斥”提升为“索引区间互斥”：

```text
范围内插入/更新 -> 被 GAP 锁阻塞，避免幻读
范围外插入/更新 -> 不与 GAP 区间冲突，可以并发执行
已有记录更新/删除 -> 由行锁保护
无索引谓词       -> 保守使用表锁，保证正确性
事务结束         -> 复用题目八的统一 unlock 路径
```

整体上既保留了 SS2PL 和 wait-die 的正确性，又缓解了表级锁带来的并发度下降问题。
