# 题目一：存储管理详解

本文档说明题目一需要实现哪些模块、每个模块要改哪些文件、每个接口的实现思路、为什么要这么实现，以及如何在 Ubuntu 环境下验证。当前代码实现基于 RMDB 框架，目标是通过 `unit_test.cpp` 中涉及的磁盘管理、缓冲池管理、LRU 替换、记录管理测试。

## 一、整体目标

题目一要求补全三个层次的存储管理能力：

1. 磁盘管理器 `DiskManager`
   - 负责文件创建、打开、关闭、删除。
   - 负责按页号读写磁盘文件中的页面。

2. 缓冲池管理器 `BufferPoolManager` 和替换器 `LRUReplacer`
   - 负责把磁盘页面缓存到内存中的固定大小缓冲池。
   - 负责页面命中、页面淘汰、脏页刷盘、pin/unpin 管理。
   - 当缓冲池满时，使用 LRU 策略选择可以淘汰的 frame。

3. 记录管理器 `RmFileHandle` 和 `RmScan`
   - 负责在表文件的数据页中插入、读取、删除、更新记录。
   - 负责维护每个数据页的 bitmap、页头、空闲页链表。
   - 负责顺序扫描表中所有有效记录。

这些模块之间的调用关系大致是：

```text
RmFileHandle / RmScan
        |
        v
BufferPoolManager
        |
        v
DiskManager
```

也就是说，记录管理器不应该直接操作磁盘数据页，而是通过缓冲池拿到 `Page`。缓冲池在需要读写磁盘时，再调用 `DiskManager`。

## 三、磁盘管理器 DiskManager

### 3.1 修改文件

```text
rmdb/src/storage/disk_manager.cpp
```

对应头文件：

```text
rmdb/src/storage/disk_manager.h
```

### 3.2 DiskManager 的职责

`DiskManager` 是最底层的存储模块，直接调用操作系统文件接口。它只关心：

- 文件是否存在。
- 文件是否已经打开。
- 文件描述符 `fd` 和文件路径之间的映射。
- 指定页号在文件中的偏移位置。
- 从文件中读写指定长度的数据。

页面大小由 `PAGE_SIZE` 定义，位置计算公式是：

```cpp
off_t pos = static_cast<off_t>(page_no) * PAGE_SIZE;
```

也就是说，第 `page_no` 页在文件中的起始偏移就是 `page_no * PAGE_SIZE`。

### 3.3 `DiskManager::write_page`

需要实现：

```cpp
void DiskManager::write_page(int fd, page_id_t page_no, const char *offset, int num_bytes);
```

实现位置：

```text
rmdb/src/storage/disk_manager.cpp
```

实现逻辑：

1. 根据 `page_no` 计算磁盘文件偏移量。
2. 调用 `lseek(fd, pos, SEEK_SET)` 把文件读写位置移动到该页开头。
3. 调用 `write(fd, offset, num_bytes)` 写入数据。
4. 如果 `lseek` 失败，抛出 `UnixError`。
5. 如果实际写入字节数不等于 `num_bytes`，抛出 `InternalError`。

为什么这么改：

- 页面是数据库存储的基本单位，缓冲池写回页面时必须写到确定的页位置。
- `lseek` 保证写入不是追加到文件末尾，而是覆盖指定页面。
- 写入字节数必须严格检查，否则磁盘数据可能只写了一半，后续读取会出现不一致。

### 3.4 `DiskManager::read_page`

需要实现：

```cpp
void DiskManager::read_page(int fd, page_id_t page_no, char *offset, int num_bytes);
```

实现逻辑：

1. 根据 `page_no` 计算文件偏移。
2. 用 `lseek` 定位到目标页面开头。
3. 用 `read` 读取 `num_bytes` 字节到 `offset`。
4. 读取失败或读取长度不足时抛出异常。

为什么这么改：

- 缓冲池 `fetch_page` 发现页面不在内存时，需要从磁盘加载完整页面。
- 测试会对磁盘和缓存中的页面内容做 `memcmp`，读取内容必须准确。
- 如果读到的字节数不足，说明文件状态和上层预期不一致，应该立刻报错。

### 3.5 `DiskManager::create_file`

需要实现：

```cpp
void DiskManager::create_file(const std::string &path);
```

实现逻辑：

1. 如果文件已经存在，抛出 `FileExistsError`。
2. 调用 `open(path.c_str(), O_CREAT | O_EXCL | O_RDWR, mode)` 创建文件。
3. 创建后立刻 `close(fd)`，因为 `create_file` 只负责创建，不负责保持打开。

为什么这么改：

- 题目要求不能重复创建同名文件。
- `O_EXCL` 可以避免并发或竞态条件下重复创建。
- 创建和打开是两个语义，测试里会先 `create_file`，再单独 `open_file`。

### 3.6 `DiskManager::open_file`

需要实现：

```cpp
int DiskManager::open_file(const std::string &path);
```

实现逻辑：

1. 如果文件不存在，抛出 `FileNotFoundError`。
2. 如果文件已经在 `path2fd_` 中，说明已经打开，抛出 `FileNotClosedError`。
3. 调用 `open(path.c_str(), O_RDWR)` 打开文件。
4. 更新两个映射：

```cpp
path2fd_[path] = fd;
fd2path_[fd] = path;
```

为什么这么改：

- `path2fd_` 用于根据文件名查找 fd。
- `fd2path_` 用于根据 fd 反查文件名。
- 这两个映射必须保持同步，否则关闭文件、删除文件、获取文件名都会出现状态错误。

### 3.7 `DiskManager::close_file`

需要实现：

```cpp
void DiskManager::close_file(int fd);
```

实现逻辑：

1. 如果 `fd2path_` 中没有该 fd，说明文件没有打开，抛出 `FileNotOpenError`。
2. 先保存对应文件名。
3. 调用 `close(fd)`。
4. 从 `fd2path_` 和 `path2fd_` 中删除映射。

为什么这么改：

- 关闭文件后，不能继续认为它处于打开状态。
- 如果只删除一个映射，另一个映射会留下脏状态，后续 `open_file` 或 `destroy_file` 会误判。

### 3.8 `DiskManager::destroy_file`

需要实现：

```cpp
void DiskManager::destroy_file(const std::string &path);
```

实现逻辑：

1. 如果文件不存在，抛出 `FileNotFoundError`。
2. 如果文件还在 `path2fd_` 中，说明文件未关闭，抛出 `FileNotClosedError`。
3. 调用 `unlink(path.c_str())` 删除文件。

为什么这么改：

- 删除不存在的文件应该报错，符合测试预期。
- 删除仍然打开的文件会让上层状态混乱，所以必须禁止。
- Unix 下 `unlink` 是删除文件目录项的标准方式。

### 3.9 构造函数初始化

原代码用 `memset` 初始化 `std::atomic<page_id_t>` 数组：

```cpp
memset(fd2pageno_, 0, ...);
```

现在改成逐个 `store(0)`：

```cpp
for (auto &page_no : fd2pageno_) {
    page_no.store(0);
}
```

为什么这么改：

- `std::atomic` 不是普通 POD 内存，直接 `memset` 在新编译器下会有警告。
- 使用 `store(0)` 是更标准的初始化方式。

### 4.1 修改文件

```text
rmdb/src/replacer/lru_replacer.cpp
```

对应头文件：

```text
rmdb/src/replacer/lru_replacer.h
```

### 4.2 数据结构含义

`LRUReplacer` 中有两个核心结构：

```cpp
std::list<frame_id_t> LRUlist_;
std::unordered_map<frame_id_t, std::list<frame_id_t>::iterator> LRUhash_;
```

含义：

- `LRUlist_` 保存当前可以被淘汰的 frame。
- 链表头部表示最久没有被使用的 frame。
- 链表尾部表示最近加入可淘汰集合的 frame。
- `LRUhash_` 用于快速判断某个 frame 是否已经在 LRU 链表中，并快速删除。

注意：只有 `pin_count_ == 0` 的页面才可以进入 replacer。正在被使用的页面不能被淘汰。

### 4.3 `LRUReplacer::victim`

需要实现：

```cpp
bool LRUReplacer::victim(frame_id_t *frame_id);
```

实现逻辑：

1. 加锁，保证并发安全。
2. 如果 `LRUlist_` 为空，返回 `false`。
3. 取链表头部 frame 作为淘汰对象。
4. 从链表和哈希表中删除它。
5. 通过 `frame_id` 返回被淘汰 frame。
6. 返回 `true`。

为什么选链表头：

- 本实现中 `unpin` 时把 frame 加到链表尾。
- 越靠前说明越早进入可淘汰状态，也就是更久没有被重新访问。
- 所以头部就是 LRU 牺牲页。

### 4.4 `LRUReplacer::pin`

需要实现：

```cpp
void LRUReplacer::pin(frame_id_t frame_id);
```

实现逻辑：

1. 加锁。
2. 如果 frame 不在 `LRUhash_`，说明它本来就不可淘汰，直接返回。
3. 如果存在，从链表删除。
4. 从哈希表删除。

为什么这么改：

- `pin` 表示页面正在被使用，不能被淘汰。
- 所以必须从 LRU 可淘汰集合中移除。

### 4.5 `LRUReplacer::unpin`

需要实现：

```cpp
void LRUReplacer::unpin(frame_id_t frame_id);
```

实现逻辑：

1. 加锁。
2. 如果 frame 已经在 replacer 中，直接返回，避免重复插入。
3. 如果 replacer 已满，直接返回。
4. 把 frame 加到 `LRUlist_` 尾部。
5. 在 `LRUhash_` 中记录它的位置。

为什么这么改：

- `unpin` 表示页面暂时没人使用，可以被淘汰。
- 同一个 frame 不能重复加入 LRU 链表，否则后续 victim 会出现重复淘汰同一 frame 的错误。
- 哈希表用于避免重复插入。

### 4.6 `LRUReplacer::Size`

实现时加锁返回 `LRUlist_.size()`。

为什么这么改：

- 测试中会检查 LRU 当前可淘汰页面数量。
- 加锁是为了并发测试中读 size 不和其他修改冲突。

## 五、BufferPoolManager

### 5.1 修改文件

```text
rmdb/src/storage/buffer_pool_manager.cpp
```

对应头文件：

```text
rmdb/src/storage/buffer_pool_manager.h
```

### 5.2 核心数据结构

```cpp
Page *pages_;
std::unordered_map<PageId, frame_id_t, PageIdHash> page_table_;
std::list<frame_id_t> free_list_;
Replacer *replacer_;
```

含义：

- `pages_` 是缓冲池中真实的 Page 数组，每个数组下标就是一个 frame。
- `page_table_` 记录磁盘页面 `PageId` 到内存 frame 的映射。
- `free_list_` 记录从未使用或已释放的空闲 frame。
- `replacer_` 记录目前可以被淘汰的 frame。

页面状态在 `Page` 中维护：

```cpp
PageId id_;
char data_[PAGE_SIZE];
bool is_dirty_;
int pin_count_;
```

### 5.3 `find_victim_page`

需要实现：

```cpp
bool BufferPoolManager::find_victim_page(frame_id_t *frame_id);
```

实现逻辑：

1. 优先从 `free_list_` 取空闲 frame。
2. 如果 `free_list_` 为空，调用 `replacer_->victim(frame_id)`。
3. 如果两者都失败，说明没有可用 frame，返回 `false`。

为什么先用 `free_list_`：

- 空闲 frame 没有旧页面，不需要刷盘和删除旧映射。
- 只有缓冲池已经没有空闲 frame 时，才需要淘汰旧页面。

### 5.4 `update_page`

需要实现：

```cpp
void BufferPoolManager::update_page(Page *page, PageId new_page_id, frame_id_t new_frame_id);
```

实现逻辑：

1. 取出旧页面 `old_page_id`。
2. 如果旧页面有效：
   - 如果是脏页，调用 `disk_manager_->write_page` 写回磁盘。
   - 从 `page_table_` 删除旧映射。
3. 重置 page 内存。
4. 更新 page 元数据：

```cpp
page->id_ = new_page_id;
page->is_dirty_ = false;
page->pin_count_ = 0;
```

5. 如果新页面有效，插入新映射：

```cpp
page_table_[new_page_id] = new_frame_id;
```

为什么这么改：

- frame 被复用时，必须先处理旧页面。
- 脏页如果不写回，会丢失用户修改。
- 页表如果不删除旧映射，同一个 frame 会被两个 PageId 指向，导致严重错误。
- 重置内存可以避免新页面读到旧页面残留数据。

### 5.5 `fetch_page`

需要实现：

```cpp
Page *BufferPoolManager::fetch_page(PageId page_id);
```

实现逻辑：

1. 加锁。
2. 在 `page_table_` 查找目标页面。
3. 如果命中：
   - 找到对应 frame。
   - `pin_count_++`。
   - 调用 `replacer_->pin(frame_id)`，确保该页不可被淘汰。
   - 返回 Page 指针。
4. 如果未命中：
   - 调用 `find_victim_page` 找可用 frame。
   - 如果找不到，返回 `nullptr`。
   - 调用 `update_page` 处理旧页并建立新映射。
   - 调用 `disk_manager_->read_page` 从磁盘读取目标页。
   - 设置 `pin_count_ = 1`，`is_dirty_ = false`。
   - 返回 Page 指针。

为什么这么改：

- 命中时不需要读磁盘，只要增加 pin 计数。
- 未命中时必须把磁盘页面读入缓冲池。
- 页面被 fetch 后说明调用者正在使用，必须 pin 住。

### 5.6 `new_page`

需要实现：

```cpp
Page *BufferPoolManager::new_page(PageId *page_id);
```

实现逻辑：

1. 加锁。
2. 找可用 frame。
3. 如果没有可用 frame，返回 `nullptr`。
4. 调用 `disk_manager_->allocate_page(page_id->fd)` 分配新页号。
5. 调用 `update_page` 复用 frame。
6. 设置新页面：

```cpp
page->pin_count_ = 1;
page->is_dirty_ = false;
```

7. 返回 Page 指针。

为什么这么改：

- `new_page` 创建的是一个全新的磁盘页面。
- 新页页号由 `DiskManager` 分配。
- 新页刚创建后在内存中被调用者使用，所以 pin count 为 1。

### 5.7 `unpin_page`

需要实现：

```cpp
bool BufferPoolManager::unpin_page(PageId page_id, bool is_dirty);
```

实现逻辑：

1. 加锁。
2. 如果页表中不存在该页面，返回 `false`。
3. 如果页面 `pin_count_ <= 0`，返回 `false`。
4. 根据参数更新脏页标记：

```cpp
page->is_dirty_ = page->is_dirty_ || is_dirty;
```

5. `pin_count_--`。
6. 如果减到 0，调用 `replacer_->unpin(frame_id)`，表示该页可以被淘汰。
7. 返回 `true`。

为什么 dirty 用或运算：

- 一个页面只要曾经被修改过，就必须保持脏页状态，直到刷盘。
- 如果已经是脏页，后续 `unpin_page(page_id, false)` 不能把它变回干净。

### 5.8 `flush_page`

需要实现：

```cpp
bool BufferPoolManager::flush_page(PageId page_id);
```

实现逻辑：

1. 加锁。
2. 如果页表中没有该页面，返回 `false`。
3. 无论是否脏页，都调用 `disk_manager_->write_page` 写回磁盘。
4. 设置 `is_dirty_ = false`。
5. 返回 `true`。

为什么不管是否脏页都写：

- 题目明确要求强制刷新时无论页面是否被使用、是否为脏页，都要写回磁盘。

### 5.9 `delete_page`

需要实现：

```cpp
bool BufferPoolManager::delete_page(PageId page_id);
```

实现逻辑：

1. 加锁。
2. 如果页面不在缓冲池中：
   - 调用 `disk_manager_->deallocate_page`。
   - 返回 `true`。
3. 如果页面在缓冲池中但 `pin_count_ != 0`，说明正在被使用，返回 `false`。
4. 如果页面可以删除：
   - 调用 `replacer_->pin(frame_id)`，确保 replacer 中没有该 frame。
   - 调用 `update_page(page, invalid_page_id, frame_id)` 清理旧页。
   - 把 frame 加回 `free_list_`。
   - 调用 `deallocate_page`。
   - 返回 `true`。

为什么正在使用时不能删除：

- pin count 不为 0 说明有上层模块持有该页指针。
- 如果此时删除或复用 frame，上层指针会指向错误数据。

### 5.10 `flush_all_pages`

需要实现：

```cpp
void BufferPoolManager::flush_all_pages(int fd);
```

实现逻辑：

1. 加锁。
2. 遍历 `page_table_`。
3. 找到所有 `page_id.fd == fd` 的页面。
4. 写回磁盘。
5. 设置页面为非脏。

为什么按 fd 过滤：

- 缓冲池可能缓存多个文件的页面。
- 关闭某个表文件时，只应该刷新该文件对应的页面。

## 六、记录管理器 RmFileHandle

### 6.1 修改文件

```text
rmdb/src/record/rm_file_handle.cpp
rmdb/src/record/rm_file_handle.h
```

### 6.2 文件头和页头

表文件第 0 页是文件头，数据页从第 1 页开始。

文件头：

```cpp
struct RmFileHdr {
    int record_size;
    int num_pages;
    int num_records_per_page;
    int first_free_page_no;
    int bitmap_size;
};
```

每个数据页的页头：

```cpp
struct RmPageHdr {
    int next_free_page_no;
    int num_records;
};
```

每个数据页布局：

```text
Page LSN 区域
RmPageHdr
bitmap
slots
```

`RmPageHandle` 封装了这些偏移：

```cpp
page_hdr = reinterpret_cast<RmPageHdr *>(page->get_data() + page->OFFSET_PAGE_HDR);
bitmap = page->get_data() + sizeof(RmPageHdr) + page->OFFSET_PAGE_HDR;
slots = bitmap + file_hdr->bitmap_size;
```

### 6.3 空闲页链表

`file_hdr_.first_free_page_no` 指向第一个未满的数据页。

每个未满页面通过：

```cpp
page_handle.page_hdr->next_free_page_no
```

串成一个链表。

当插入记录导致页面满了：

- 该页面需要从空闲页链表中移除。
- `file_hdr_.first_free_page_no` 改成该页的下一个空闲页。

当删除记录导致页面从满变为未满：

- 该页面需要重新加入空闲页链表头部。

### 6.4 `fetch_page_handle`

需要实现：

```cpp
RmPageHandle RmFileHandle::fetch_page_handle(int page_no) const;
```

实现逻辑：

1. 检查 `page_no` 是否是合法数据页。
2. 如果小于 `RM_FIRST_RECORD_PAGE` 或大于等于 `file_hdr_.num_pages`，抛出 `PageNotExistError`。
3. 调用 `buffer_pool_manager_->fetch_page(PageId{fd_, page_no})`。
4. 如果返回空指针，抛出 `InternalError`。
5. 用拿到的 `Page *` 构造 `RmPageHandle` 返回。

为什么这么改：

- 记录管理层必须通过缓冲池访问页面。
- 返回 `RmPageHandle` 后，上层可以方便访问页头、bitmap 和 slot。
- 调用者使用完后必须 unpin 页面。

### 6.5 `create_new_page_handle`

需要实现：

```cpp
RmPageHandle RmFileHandle::create_new_page_handle();
```

实现逻辑：

1. 调用 `buffer_pool_manager_->new_page(&page_id)` 创建新页。
2. 初始化新页页头：

```cpp
page_handle.page_hdr->next_free_page_no = file_hdr_.first_free_page_no;
page_handle.page_hdr->num_records = 0;
```

3. 初始化 bitmap：

```cpp
Bitmap::init(page_handle.bitmap, file_hdr_.bitmap_size);
```

4. 更新文件头：

```cpp
file_hdr_.num_pages++;
file_hdr_.first_free_page_no = page_id.page_no;
```

5. 返回新页面 handle。

为什么这么改：

- 新页面一开始没有记录，所以一定是空闲页。
- 把新页插到空闲页链表头部，可以让下一次插入直接使用。
- `num_pages` 必须递增，否则关闭文件后重新打开，文件头不知道已有新页面。

### 6.6 `create_page_handle`

需要实现：

```cpp
RmPageHandle RmFileHandle::create_page_handle();
```

实现逻辑：

1. 如果 `file_hdr_.first_free_page_no == RM_NO_PAGE`，说明没有空闲页，创建新页。
2. 否则直接 fetch 第一个空闲页。

为什么这么改：

- 插入记录时只需要找到一个有空 slot 的页面。
- 文件头已经维护了空闲页链表头，直接使用即可。

### 6.7 `get_record`

需要实现：

```cpp
std::unique_ptr<RmRecord> RmFileHandle::get_record(const Rid &rid, Context *context) const;
```

实现逻辑：

1. fetch 记录所在页面。
2. 检查 slot 是否越界。
3. 检查 bitmap 对应位是否为 1。
4. 如果记录不存在，unpin 页面并抛出 `RecordNotFoundError`。
5. 根据 slot 数据构造 `RmRecord`。
6. unpin 页面。
7. 返回记录。

为什么这么改：

- `Rid` 中的 `page_no` 和 `slot_no` 唯一定位一条记录。
- bitmap 为 1 才代表该 slot 中有有效记录。
- 返回 `RmRecord` 时要拷贝数据，不能直接返回指向 page 内部的裸指针，否则页面被淘汰后记录数据会失效。

### 6.8 `insert_record(char *buf, Context *context)`

需要实现：

```cpp
Rid RmFileHandle::insert_record(char *buf, Context *context);
```

实现逻辑：

1. 调用 `create_page_handle` 找到一个未满页面。
2. 在 bitmap 中找第一个 0 位：

```cpp
int slot_no = Bitmap::first_bit(false, page_handle.bitmap, file_hdr_.num_records_per_page);
```

3. 设置 bitmap 对应位为 1。
4. 把 `buf` 拷贝到 slot。
5. 页面记录数加 1。
6. 如果插入后页面满了：
   - `file_hdr_.first_free_page_no` 指向当前页的下一个空闲页。
   - 当前页 `next_free_page_no` 置为 `RM_NO_PAGE`。
7. unpin 页面并标记 dirty。
8. 返回新记录的 `Rid`。

为什么这么改：

- bitmap 是判断 slot 是否被占用的权威来源。
- 插入后页头和文件头必须同步更新，否则后续插入会找错空闲页。
- 页面内容发生变化，所以 unpin 时 `is_dirty` 必须传 `true`。

### 6.9 `insert_record(const Rid &rid, char *buf)`

需要实现：

```cpp
void RmFileHandle::insert_record(const Rid &rid, char *buf);
```

这个接口主要用于事务回滚和恢复，需要支持在指定位置插入。

实现逻辑：

1. 如果指定 `rid.page_no` 超过当前页数，循环创建新页直到页号合法。
2. fetch 指定页面。
3. 检查 slot 合法性。
4. 如果该 slot 原来为空：
   - 设置 bitmap。
   - 页记录数加 1。
5. 拷贝记录内容到指定 slot。
6. 如果页面因此变满，并且它正好是空闲链表头，则从空闲链表移除。
7. unpin 页面并标记 dirty。

为什么这么改：

- 恢复场景可能要求把记录恢复到原来的 Rid。
- 指定插入不能自己另找 slot，否则无法恢复原始位置。

### 6.10 `delete_record`

需要实现：

```cpp
void RmFileHandle::delete_record(const Rid &rid, Context *context);
```

实现逻辑：

1. fetch 记录所在页面。
2. 检查 slot 合法性和 bitmap。
3. 如果记录不存在，抛出 `RecordNotFoundError`。
4. 记录删除前先判断页面是否是满的：

```cpp
bool was_full = page_handle.page_hdr->num_records == file_hdr_.num_records_per_page;
```

5. bitmap 对应位清零。
6. slot 内容清零。
7. 页记录数减 1。
8. 如果页面之前是满的，删除后变成未满，调用 `release_page_handle` 加回空闲链表。
9. unpin 页面并标记 dirty。

为什么只在之前满时 release：

- 如果页面删除前本来就未满，它已经在空闲页链表中。
- 再次加入会造成链表重复，后续插入可能出现循环或重复页面。

### 6.11 `update_record`

需要实现：

```cpp
void RmFileHandle::update_record(const Rid &rid, char *buf, Context *context);
```

实现逻辑：

1. fetch 记录所在页面。
2. 检查 slot 是否合法，记录是否存在。
3. 把新数据拷贝到原 slot。
4. unpin 页面并标记 dirty。

为什么这么改：

- 更新记录不改变 bitmap。
- 更新记录不改变页面记录数。
- 只修改 slot 内容，所以只需要标 dirty。

### 6.12 `release_page_handle`

需要实现：

```cpp
void RmFileHandle::release_page_handle(RmPageHandle &page_handle);
```

实现逻辑：

把当前页面插入空闲页链表头：

```cpp
page_handle.page_hdr->next_free_page_no = file_hdr_.first_free_page_no;
file_hdr_.first_free_page_no = page_handle.page->get_page_id().page_no;
```

为什么这么改：

- 删除记录后，如果页面从满变未满，就应该再次成为可插入页面。
- 插到链表头实现简单，后续插入可以马上复用这个页面。

### 6.13 `is_record` 的修正

文件：

```text
rmdb/src/record/rm_file_handle.h
```

原接口里 `is_record` 调用了 `fetch_page_handle`，但是没有 unpin 页面。

修正后逻辑：

1. fetch 页面。
2. 检查 bitmap。
3. unpin 页面。
4. 返回检查结果。

为什么需要改：

- `fetch_page_handle` 会导致页面 pin count 增加。
- 如果不 unpin，测试中反复调用 `is_record` 会让页面一直处于 pinned 状态。
- 页面无法进入 replacer，缓冲池满时就可能找不到可淘汰页面。

## 七、RmScan

### 7.1 修改文件

```text
rmdb/src/record/rm_scan.cpp
```

### 7.2 RmScan 的职责

`RmScan` 用于遍历表中所有有效记录。它不是遍历所有 slot，而是跳过 bitmap 为 0 的空 slot。

### 7.3 构造函数

需要实现：

```cpp
RmScan::RmScan(const RmFileHandle *file_handle);
```

实现逻辑：

1. 保存 `file_handle_`。
2. 初始化 `rid_` 为第一个数据页之前的起点：

```cpp
rid_ = Rid{RM_FIRST_RECORD_PAGE, -1};
```

3. 调用 `next()` 找到第一条有效记录。

为什么 slot 从 -1 开始：

- `Bitmap::next_bit` 查找范围是从 `curr + 1` 开始。
- 如果要从 slot 0 开始找，初始 curr 应该是 -1。

### 7.4 `next`

需要实现：

```cpp
void RmScan::next();
```

实现逻辑：

1. 从当前 `rid_` 所在位置继续找。
2. fetch 当前页。
3. 调用：

```cpp
Bitmap::next_bit(true, page_handle.bitmap, num_records_per_page, slot_no);
```

4. 如果找到有效 slot，更新 `rid_` 并返回。
5. 如果当前页没有更多有效记录，unpin 当前页，进入下一页，slot 从 -1 开始。
6. 如果所有页都扫描完，设置：

```cpp
rid_ = Rid{file_hdr_.num_pages, -1};
```

为什么扫描时每页都要 unpin：

- 扫描只是短暂读取 bitmap，不应该长期占用页面。
- 如果扫描不 unpin，会影响缓冲池淘汰。

### 7.5 `is_end`

需要实现：

```cpp
bool RmScan::is_end() const;
```

实现逻辑：

```cpp
return rid_.page_no >= file_handle_->file_hdr_.num_pages;
```

为什么这么改：

- 数据页合法范围是 `[RM_FIRST_RECORD_PAGE, file_hdr_.num_pages)`。
- 当 `rid_.page_no == file_hdr_.num_pages` 时，说明已经越过最后一页。

## 十、实现中的关键原则

### 10.1 页面被 fetch 后必须 unpin

只要调用了：

```cpp
buffer_pool_manager_->fetch_page(...)
```

就会让页面 pin count 增加。使用完后必须调用：

```cpp
buffer_pool_manager_->unpin_page(page_id, is_dirty);
```

否则页面会一直不能被淘汰。

### 10.2 修改页面内容必须标 dirty

以下操作会修改页面内容，unpin 时必须传 `true`：

- 插入记录。
- 删除记录。
- 更新记录。
- 初始化新数据页。

只读取页面时传 `false`。

### 10.3 脏页淘汰前必须写回

缓冲池复用 frame 时，如果旧页是脏页，必须先写回磁盘：

```cpp
if (page->is_dirty_) {
    disk_manager_->write_page(...);
}
```

否则修改会丢失。

### 10.4 页表必须和 Page 元数据同步

当 frame 从旧页面切换为新页面时：

- 删除旧 `PageId -> frame_id` 映射。
- 重置 Page 内存和元数据。
- 插入新 `PageId -> frame_id` 映射。

如果页表和 Page 元数据不同步，会导致 fetch 到错误页面。

### 10.5 空闲页链表只维护未满页

记录管理中：

- 未满页应该出现在空闲页链表中。
- 满页不应该出现在空闲页链表中。
- 页面从未满变满时，要从链表移除。
- 页面从满变未满时，要加入链表。

这是插入记录能高效找到空 slot 的关键。

## 十二、后续维护建议

如果后面继续做事务、日志、恢复或索引模块，题目一这些接口会成为基础依赖。需要特别注意：

1. 不要绕过 `BufferPoolManager` 直接修改数据页。
2. 不要忘记 unpin。
3. 不要在记录层手动写磁盘页面，交给缓冲池 flush。
4. 文件头第 0 页目前由 `RmManager::close_file` 直接写回，这和数据页经缓冲池管理是两条路径，不能混淆。
5. 如果后续加入日志，需要在修改页面前后配合日志 LSN，但题目一阶段暂不处理。
