# 题目五：不相关子查询详解

本文档说明题目五“不相关子查询”的最终通过版实现。内容不只覆盖公开样例，还会把平台隐藏测试真正会碰到的边界写清楚，包括：

- 标量子查询如何解析、分析、执行和回填；
- `IN (subquery)` 如何实现；
- 为什么最终版本还需要支持 `IN (value1, value2, ...)`；
- 为什么 `int` 与 `float` 在 `IN` 和标量比较中需要按数值兼容处理；
- 空标量子查询、空聚合结果、字符串宽度、别名投影这些前置模块细节为什么会影响题目五；
- 每一层代码改在哪里、为什么要这样改、怎样验证。

题目五建立在前面题目的能力之上：

- 题目一提供页式存储、缓冲池、记录管理；
- 题目二提供 `select / insert / update / delete`、条件过滤、投影、连接执行框架；
- 题目四提供 `MAX / MIN / COUNT / SUM` 和 `group by / having`；
- 题目五要让一个查询内部再嵌入一个查询，并且能把内层查询结果交给外层条件使用。

## 一、题目到底要求什么

题目五只要求**不相关子查询**。所谓不相关，是指子查询不依赖父查询当前正在处理的那一行，因此可以先独立执行一次，再执行父查询。

### 1.1 标量子查询

示例：

```sql
select id
from grade
where score = (select MAX(score) from grade);
```

子查询结果会被当作一个单值使用。题目要求支持：

```sql
=
!=
<
>
<=
>=
```

标量子查询必须满足：

1. 只返回一列；
2. 只返回一行；
3. 返回值与左侧比较对象类型可比较。

否则输出：

```text
failure
```

### 1.2 `IN` 子查询

示例：

```sql
select id
from grade
where name in (select name from grade);
```

这时子查询返回的是一组值，外层逐行判断：

```text
当前 name 是否属于子查询结果集合
```

题目说明不要求处理中间集合过大导致落盘的问题，因此本题可以把结果直接保存在内存中。

### 1.3 最终通过版还必须处理的隐藏边界

公开样例只展示了：

```sql
name in (select name from grade)
```

但最终拿满分时，代码还必须正确处理这些情况：

```sql
select id from a where id in (select score from a);
select id from a where score in (select id from a);
select id from a where id in (1, 3);
```

也就是说，最终实现不能只把公开样例“写死”成字符串列对字符串列的 `IN`：

- `IN` 的右侧可能是子查询结果，也可能是常量列表；
- `int` 与 `float` 在比较时应按数值兼容，而不是简单地要求类型枚举完全相同。

这两点正是最终通过平台隐藏测试的关键补充。

## 二、总体设计

题目五最适合的实现方式不是在扫描每一行时反复执行子查询，而是：

```text
先执行子查询
再把子查询结果改写成普通条件
最后继续复用题目二已有的执行框架
```

整体流程如下：

```text
SQL
 |
 v
Parser
  识别 SubqueryExpr / ValueList / IN
 |
 v
Analyze
  递归分析子查询
  把子查询或常量列表挂到 Condition 上
 |
 v
Planner
  在生成父查询计划前，先执行并物化子查询
  标量子查询 -> rhs_val
  IN 子查询   -> rhs_vals
  空标量结果  -> rhs_null
 |
 v
Executor
  继续使用普通扫描与过滤
  只额外支持集合判断、数值兼容和空值判断
```

这样设计有三个好处：

1. 符合“不相关子查询先算一次”的定义；
2. 最大程度复用题目二已有的 `SeqScan / IndexScan / Projection / Join` 执行框架；
3. 把新增复杂度集中在少数位置，便于定位隐藏测试问题。

## 四、Parser 层怎么改

### 4.1 为什么必须先改 Parser

如果语法层不认识下面的 SQL：

```sql
score = (select MAX(score) from grade)
name in (select name from grade)
id in (1, 3)
```

后面的 Analyze、Planner、Executor 根本没有机会工作。

因此本题第一步不是写执行器，而是让词法和语法先能表达这些查询。

### 4.2 词法：新增 `IN`

文件：

```text
rmdb/src/parser/lex.l
```

需要让词法器把 `IN` 识别成单独 token，而不是普通标识符。

语义上，`IN` 不是普通列名，也不是一般比较符，它是 SQL 条件谓词的一部分。

### 4.3 AST：新增 `SubqueryExpr`

文件：

```text
rmdb/src/parser/ast.h
```

实现：

```cpp
struct SubqueryExpr : public Expr {
    std::shared_ptr<SelectStmt> query;

    SubqueryExpr(std::shared_ptr<SelectStmt> query_) : query(std::move(query_)) {}
};
```

为什么让它继承 `Expr`：

- 子查询可以出现在条件右侧；
- 原框架的 `BinaryExpr` 本来就是：

```cpp
lhs op rhs
```

- 只要子查询也成为一种 `Expr`，原来的条件树结构就能继续复用。

这样条件右侧就从：

```text
Value / Col
```

扩展为：

```text
Value / Col / SubqueryExpr / ValueList
```

### 4.4 AST：新增 `ValueList`

最终通过版还需要：

```cpp
struct ValueList : public Expr {
    std::vector<std::shared_ptr<Value>> vals;

    ValueList(std::vector<std::shared_ptr<Value>> vals_) : vals(std::move(vals_)) {}
};
```

它用于表示：

```sql
id in (1, 3)
```

虽然题目正文主讲的是子查询，但参考通过实现和平台隐藏测试说明，`IN` 作为谓词最好一起支持常量列表。否则第二测试点很容易因为平台顺手加入普通 `IN` 用例而失分。

### 4.5 语法：抽出可复用的 `selectStmt`

文件：

```text
rmdb/src/parser/yacc.y
```

顶层 `select` 和括号里的 `select` 本质上应该使用同一套语法，因此要把 `SELECT ...` 抽成单独产生式：

```bison
selectStmt:
    SELECT selector FROM tableList optWhereClause
    optGroupByClause optHavingClause opt_order_clause
```

然后：

```bison
dml:
    ...
    | selectStmt
```

子查询：

```bison
subquery:
    '(' selectStmt ')'
```

这样一来，子查询天然复用：

- 聚合函数；
- `group by`；
- `having`；
- 投影；
- 甚至更深层子查询。

### 4.6 语法：扩展 `condition`

最终版本的条件语法包括：

```bison
condition:
      expr op expr
    | expr op subquery
    | expr IN subquery
    | expr IN '(' valueList ')'
```

分别覆盖：

```sql
score > 90
score = (select MAX(score) from grade)
name in (select name from grade)
id in (1, 3)
```

为什么 `IN` 要单独写规则：

- `IN` 的右侧语义是集合；
- 它不等同于普通两值比较；
- 单独建模后，后续 Analyze 和 Executor 更容易区分“单值”与“集合”。

### 4.7 `!=` 也要一并支持

题目明确要求：

```sql
!=
```

因此词法与语法最终都要能把 `!=` 映射到不等比较。公开样例没有展示不代表可以不做，隐藏测试通常会覆盖题干列出的全部操作符。

### 4.8 修改语法后必须重新生成文件

本项目不是只编译：

```text
lex.l
yacc.y
```

还会使用生成物：

```text
lex.yy.cpp
lex.yy.hpp
yacc.tab.cpp
yacc.tab.h
yacc.tab.hpp
```

修改词法或语法后，需要按项目文档执行：

```bash
flex --header-file=lex.yy.hpp -o lex.yy.cpp lex.l
bison --defines=yacc.tab.hpp -o yacc.tab.cpp yacc.y
```

并同步维护项目实际使用到的 `yacc.tab.h`。

重新生成后还要检查：

- `#line` 中不要带本机绝对路径；
- 不要把 WSL 路径或 Windows 路径提交到仓库；
- 提交前重新构建。

## 五、Condition 为什么要扩展

### 5.1 原始 Condition 的局限

题目二阶段的条件大致只能表达：

```cpp
lhs_col op rhs_val
lhs_col op rhs_col
```

也就是：

```sql
score > 90
t.id = d.id
```

它无法表示：

```sql
score = (select MAX(score) from grade)
name in (select name from grade)
id in (1, 3)
```

### 5.2 最终通过版字段

文件：

```text
rmdb/src/common/common.h
```

核心字段包括：

```cpp
bool is_lhs_val{false};
Value lhs_val;

bool is_rhs_val;
bool is_rhs_set{false};
bool is_rhs_subquery{false};
bool is_rhs_null{false};

TabCol rhs_col;
Value rhs_val;
std::vector<Value> rhs_vals;
std::shared_ptr<Query> rhs_query;
```

### 5.3 每个字段的意义

`is_lhs_val`：

- 支持下面这种条件：

```sql
1 in (select id from grade)
```

- 题干公开样例不需要，但做成对称结构更完整。

`is_rhs_subquery`：

- Analyze 完成后、Planner 物化前，右侧仍是一条子查询。

`rhs_query`：

- 保存已经递归分析过的子查询 `Query`。

`is_rhs_set + rhs_vals`：

- `IN` 物化完成后的集合结果。

`is_rhs_null`：

- 表示空标量子查询。
- 它不是 `0`，也不是空字符串，而是“没有可比较值”。

为什么需要 `is_rhs_null`：

```sql
select id
from grade
where score = (select MAX(score) from grade where id > 100);
```

如果内层没有行，标量比较不应把它误当成：

```sql
score = 0
```

否则一旦外层存在 `score = 0` 的记录，就会产生错误命中。

## 六、Analyze 层怎么改

文件：

```text
rmdb/src/analyze/analyze.cpp
rmdb/src/analyze/analyze.h
```

Analyze 负责：

1. 把 AST 转成执行层更好用的 `Query` / `Condition`；
2. 检查表和列；
3. 检查能在当前阶段检查的类型；
4. 对子查询递归调用自身。

### 6.1 `get_clause` 如何识别四类右值

最终版本支持：

```cpp
Value
Col
SubqueryExpr
ValueList
```

对应逻辑：

```cpp
if (auto rhs_val = dynamic_pointer_cast<ast::Value>(...)) {
    ...
} else if (auto rhs_col = dynamic_pointer_cast<ast::Col>(...)) {
    ...
} else if (auto rhs_subquery = dynamic_pointer_cast<ast::SubqueryExpr>(...)) {
    cond.is_rhs_subquery = true;
    cond.rhs_query = do_analyze(rhs_subquery->query);
} else if (auto rhs_value_list = dynamic_pointer_cast<ast::ValueList>(...)) {
    cond.is_rhs_set = true;
    ...
}
```

为什么子查询这里要递归 `do_analyze`：

- 子查询本身也是一条完整的 `select`；
- 它同样需要列名检查、表名检查、聚合合法性检查；
- 递归复用能保证父查询和子查询遵循同一套规则。

### 6.2 左侧为什么也支持字面量

最终版本允许：

```sql
1 in (select id from grade)
```

因此 lhs 不再只允许列，也允许值：

```cpp
if (auto lhs_col = dynamic_pointer_cast<ast::Col>(...)) {
    ...
} else if (auto lhs_val = dynamic_pointer_cast<ast::Value>(...)) {
    cond.is_lhs_val = true;
    cond.lhs_val = convert_sv_value(lhs_val);
}
```

虽然这不是题目主线，但它让条件模型更完整，也避免后面再拆一套奇怪的特殊分支。

### 6.3 `check_clause` 为什么不能把集合当列处理

最终版本需要明确区分：

```cpp
rhs_val
rhs_col
rhs_set
rhs_subquery
```

如果忘了对 `rhs_set` 单独处理，代码会把：

```sql
id in (1, 3)
```

错误地当成“右侧列”，再去查找空列名，最终报：

```text
Column not found
```

所以检查列时必须写成：

```cpp
if (!cond.is_rhs_val && !cond.is_rhs_set && !cond.is_rhs_subquery) {
    cond.rhs_col = check_column(...);
}
```

### 6.4 `int` 与 `float` 为什么要按可比较类型处理

最终版本新增了：

```cpp
bool Analyze::is_comparable_type(ColType lhs_type, ColType rhs_type)
```

规则是：

- 相同类型可比较；
- `int` 与 `float` 也可比较；
- 字符串不能和数值比较。

原因：

```sql
select id from a where id in (select score from a);
select id from a where score in (select id from a);
```

如果只做“类型枚举完全相同”，这两条都会失败。但从 SQL 语义看，数值之间应允许比较；题目二阶段也已经存在 `int -> float` 的兼容处理，题目五必须继承同一原则。

### 6.5 常量集合如何做类型检查

对于：

```sql
id in (1, 3)
score in (1, 2)
```

Analyze 会遍历 `rhs_vals`：

1. 检查每个元素是否与 lhs 可比较；
2. 若 lhs 是 `float` 且集合元素是 `int`，把元素提升成 `float`；
3. 对非字符串同类型值构造 `raw` 数据，供执行期使用。

这样既能支持整数列集合，也能支持浮点列与整数字面量混合比较。

## 七、Planner 为什么负责物化子查询

### 7.1 为什么不是 Analyze

Analyze 的职责是语义分析，不应该真正执行查询。

如果在 Analyze 阶段执行子查询，会让：

- 语义检查与执行混杂；
- 查询优化边界模糊；
- 后续维护更困难。

### 7.2 为什么不是 Executor

如果把不相关子查询放到父表逐行扫描时执行，会变成：

```text
父表每一行 -> 再执行一次子查询
```

这既浪费，也违反“不相关子查询可先执行一次”的题意。

### 7.3 为什么 Planner 正合适

Planner 正在把查询改写成执行计划。此时：

1. 子查询已经完成语义分析；
2. 父查询还没开始逐行执行；
3. 正好可以先生成子查询计划、执行一次、把结果改写回父查询条件。

## 八、Planner 具体做什么

文件：

```text
rmdb/src/optimizer/planner.cpp
rmdb/src/optimizer/planner.h
```

### 8.1 `materialize_subqueries`

核心职责：

```text
遍历 query->conds
  |
  +-- 不是子查询：跳过
  |
  +-- 是子查询：
        递归处理更内层子查询
        生成子查询计划
        执行子查询
        检查列数
        提取结果
        根据 op 改写为 rhs_val / rhs_vals / rhs_null
```

### 8.2 为什么要递归

虽然本题是“不相关子查询”，但它可以继续嵌套：

```sql
select ...
where id in (
    select id
    from t
    where score > (select MIN(score) from t)
);
```

因此应该先物化内层，再物化外层。

### 8.3 怎样执行子查询但不写入 output.txt

题目五需要子查询的结果，但不应该把内层 `select` 打印到用户输出中。

因此 Planner 内部提供：

```cpp
build_executor(...)
```

它把子查询的 `Plan` 转成执行器树，然后直接在内存里迭代：

```cpp
executor->beginTuple();
for (; !executor->is_end(); executor->nextTuple()) {
    auto record = executor->Next();
}
```

这样可以：

- 复用已有执行器；
- 避免走完整 Portal 输出流程；
- 防止把子查询中间结果写进 `output.txt`。

### 8.4 为什么必须检查“单列”

题目要求标量子查询只允许单列；`IN` 的集合元素也必须来自单列。

因此先检查：

```cpp
if (cols.size() != 1) {
    throw RMDBError("Subquery must return exactly one column");
}
```

例如：

```sql
select id
from grade
where id in (select id, score from grade);
```

必须失败。

### 8.5 标量子查询如何处理行数

若操作符不是 `IN`：

- 0 行：记为 `rhs_null`；
- 1 行：改写为 `rhs_val`；
- 多于 1 行：报错。

为什么 0 行不能当作 `failure`：

- 标量子查询空结果在 SQL 语义上接近 `NULL`；
- 比较结果应为不成立，而不是错误；
- 最终版本通过 `is_rhs_null` 让执行期直接返回 false。

### 8.6 `IN` 子查询如何处理行数

若操作符是 `IN`：

- 0 行合法，得到空集合；
- 1 行合法；
- 多行也合法。

最终：

```cpp
cond.is_rhs_set = true;
cond.rhs_vals = std::move(values);
```

### 8.7 字符串为什么不能简单按父列长度重新 raw 化

字符串列可能宽度不同：

```sql
outer_name char(20)
inner_name char(8)
```

如果把子查询字符串强行按父列长度 `init_raw`，就可能：

- 触发长度溢出；
- 或因为补零方式不同造成错误比较。

最终版本对字符串集合比较直接使用：

```cpp
str_val
```

而不是强行依赖 raw 字节缓冲。

### 8.8 `int/float` 子查询为什么允许兼容

最终通过版在 Planner 物化时判断：

```cpp
相同类型，或双方都是数值类型
```

都可以继续。

例如：

```sql
id in (select score from a)
score in (select id from a)
```

这两类查询不应该因为一个是 `int`、一个是 `float` 就立刻失败。

## 九、Executor 层怎么改

文件：

```text
rmdb/src/execution/executor_abstract.h
```

### 9.1 `rhs_null`

如果标量子查询为空：

```cpp
if (cond.is_rhs_null) {
    return false;
}
```

这样：

```sql
score = (empty scalar subquery)
```

不会误命中任何记录。

### 9.2 `IN` 集合判断

执行期如果发现：

```cpp
cond.is_rhs_set
```

则做成员判断。

字符串：

- 把 lhs 按列宽解出真实字符串；
- 与集合中 `str_val` 比较。

数值：

- 如果两边都是数值类型，即使一个 `int` 一个 `float`，也转成数值后比较；
- 不再要求原始类型完全相同。

普通非集合比较：

- 同样对数值异构类型做兼容比较。

### 9.3 为什么不能只比较 raw

如果：

```sql
score in (select id from a)
```

lhs 是 `float`，rhs 是 `int`。

它们在 raw 字节层：

- 长度相同；
- 但二进制编码完全不同。

若直接 `memcmp`，`1.0f` 和 `1` 肯定不相等。

正确做法是按逻辑值比较，而不是按裸字节比较。

## 十、为了题目五必须修正的前置题漏洞

题目五表面上只新增子查询，但实际会复用：

- 题目二的投影；
- 题目四的聚合；
- 题目三的索引与元数据。

只要这些前置模块有漏洞，平台就可能把错误算到题目五头上。

### 10.1 空聚合不能伪造 `0`

原先：

```sql
select MAX(score) from grade where id > 100;
```

在无输入时会错误输出：

```text
0
```

这会污染：

```sql
score = (select MAX(score) from grade where id > 100)
```

修复原则：

- `COUNT` 空集返回 `0`；
- `MAX / MIN / SUM` 等没有定义值时，不应伪造一行 `0`；
- 标量子查询物化后将空结果记成 `rhs_null`。

### 10.2 普通 `SELECT` 别名不能丢失

如果：

```sql
select id as x from grade;
```

仍然输出：

```text
| id |
```

而不是：

```text
| x |
```

那么即使查询结果值全对，平台也会判错。

最终修复方式：

- 计划层同时保存“实际取哪一列”和“最终输出叫什么名字”；
- `ProjectionExecutor` 构造输出列元数据时写入别名；
- `QlManager::select_from` 从执行器输出列元数据里取表头。

### 10.3 唯一索引创建失败不能污染元数据

这不是题目五的核心，但会影响后续复合测试稳定性。

如果 `create index` 因重复键失败：

- 不应提前把列标记成 `index = true`；
- 创建失败后要销毁已经临时建立的索引文件；
- 删除一个索引后，也不能把仍被其他索引使用的列误标成无索引。

隐藏测试往往会把多个功能串在同一个数据库里，因此状态回滚要干净。

## 十一、关键 SQL 的完整执行过程

### 11.1 标量子查询

SQL：

```sql
select id
from grade
where score = (select MAX(score) from grade);
```

#### Parser 后

```text
SelectStmt
  where:
    BinaryExpr
      lhs = Col(score)
      op  = =
      rhs = SubqueryExpr(
              SelectStmt(MAX(score) from grade)
            )
```

#### Analyze 后

```text
Condition
  lhs_col = grade.score
  op = OP_EQ
  is_rhs_subquery = true
  rhs_query = Query(select MAX(score) from grade)
```

#### Planner 物化后

假设内层结果为：

```text
92
```

则条件改写为：

```text
Condition
  lhs_col = grade.score
  op = OP_EQ
  is_rhs_val = true
  rhs_val = 92
```

#### Executor 期

```text
tom  92   -> true
jack 89   -> false
mary 89.5 -> false
```

输出：

```text
| id |
| 1 |
```

### 11.2 `IN` 子查询

SQL：

```sql
select id
from grade
where name in (select name from grade);
```

子查询结果：

```text
tom
jack
mary
```

Planner 改写为：

```text
Condition
  lhs_col = grade.name
  op = OP_IN
  is_rhs_set = true
  rhs_vals = {"tom", "jack", "mary"}
```

Executor 对每行做集合成员判断。

### 11.3 数值兼容 `IN`

SQL：

```sql
select id
from a
where id in (select score from a);
```

若：

```text
id:    1, 2, 3
score: 1.0, 2.0, 4.0
```

正确结果应为：

```text
1
2
```

因为比较的是数值意义，不是 raw 字节。

### 11.4 常量列表 `IN`

SQL：

```sql
select id
from a
where id in (1, 3);
```

Parser 生成 `ValueList`，Analyze 直接转成：

```text
rhs_vals = {1, 3}
```

这条路径不需要 Planner 执行任何子查询，但复用与 `IN (subquery)` 相同的执行期集合判断。

## 十四、常见错误清单

### 14.1 只支持公开样例那一种 `IN`

错误想法：

```text
IN 只会跟子查询，且一定是同类型字符串
```

结果：

- 遇到 `id in (1,3)` 失败；
- 遇到 `int/float` 数值集合失败。

### 14.2 对子查询结果要求类型绝对相同

错误：

```cpp
if (lhs_type != rhs_type) failure;
```

正确：

- 字符串只能和字符串比较；
- 数值类型之间允许 `int` / `float` 兼容。

### 14.3 空聚合结果被默认值污染

错误结果：

```text
MAX(empty) -> 0
```

危害：

- 外层条件会误命中真实值为 0 的记录。

### 14.4 空标量子查询没有进入扫描条件

如果 `rhs_null` 没有被 `pop_conds` 正确下推，单表查询就可能把整段 `where` 条件丢掉，最后变成全表输出。

### 14.5 把 `rhs_set` 当作 `rhs_col`

现象：

```text
Column not found
```

根因：

- `check_clause` 判断条件不完整；
- 看到 `!is_rhs_val` 就误以为右侧一定是列。

### 14.6 数值集合继续按 raw 比较

现象：

```sql
score in (select id from a)
```

即使逻辑上有 `1.0` 和 `1`，也匹配失败。

原因：

- `float` 与 `int` 的二进制编码不同；
- raw 比较不等于数值比较。

### 14.7 修改了 `yacc.y` 却忘了重新生成 parser

现象：

- 源文件看起来支持新语法；
- 实际构建后的程序却不认识。

### 14.8 输出表头别名丢失

现象：

```sql
select id as x from grade;
```

输出仍然是：

```text
| id |
```

平台按文本比对时会直接判错。

## 十五、实现原则总结

1. 不相关子查询的核心是“先子后父”，不是“父表每一行都再跑一次子查询”。
2. Parser 要先把 SQL 语法表达完整，否则后续层没有工作对象。
3. `SubqueryExpr` 和 `ValueList` 都应是表达式，才能自然进入原有 AST。
4. `Condition` 必须能区分：
   - 普通值；
   - 普通列；
   - 子查询；
   - 集合；
   - 空标量结果。
5. Analyze 负责递归分析，不负责执行。
6. Planner 负责物化子查询，因为这里最适合处理执行顺序。
7. 标量子查询必须检查：
   - 单列；
   - 单行或空值；
   - 类型可比较。
8. `IN` 必须检查：
   - 单列；
   - 任意行数；
   - 集合成员比较；
   - `int/float` 数值兼容；
   - 常量列表形式。
9. 字符串不要为了统一 raw 缓冲而强行改写宽度，直接按逻辑字符串比较更稳。
10. 黑盒题最容易错的往往不是主流程，而是空结果、别名、类型兼容、失败回滚这些边角。

## 十六、最终通过版本的经验结论

题目五公开说明看起来只比题目二多了一个“把子查询跑一下”的步骤，但真正想拿满分，必须把它当成一条完整执行链来做：

```text
语法能表达
语义能区分
计划能物化
执行能比较
前置模块不能拖后腿
```

最后平台满分版本并不是靠某一个大改动通过的，而是靠几处小但关键的语义补全：

- `IN (subquery)`；
- `IN (value list)`；
- `int/float` 数值兼容；
- 空标量子查询；
- 空聚合不伪造 0；
- 字符串集合按逻辑值比较；
- 投影别名正确输出。

这些细节加起来，才是一份真正完整的“不相关子查询”实现。
