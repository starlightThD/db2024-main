# 题目八：冲突可串行化详解

本文档说明题目八“冲突可串行化”的完整实现方式。内容主要为：
题目要求分析、
总体并发控制设计、
锁管理器实现、
wait-die 死锁预防策略、
执行器加锁入口、
事务结束释放锁、
DDL 加锁、
五类数据异常如何避免、
本地和平台验证结果。

本题建立在前序题目的能力之上：
1. 题目二已经打通 `insert / delete / update / select` 的基本执行链路。
2. 题目三已经实现唯一索引，以及 DML 执行时对索引的同步维护和唯一性检查。
3. 题目七已经实现显式事务控制，`Transaction` 的 `write_set_` 可以在 `abort` 中逆序回滚基表记录和索引项。
4. 本题需要在这些能力外面补齐并发控制，使多个客户端事务并发执行时仍满足可串行化隔离级别。

## 一、题目要求分析

题目要求系统支持并发事务，并使用强严格两阶段封锁协议：

```text
Strong Strict Two-Phase Locking, SS2PL
```

目标隔离级别是：

```text
Serializable
```

测试重点会覆盖五类典型数据异常：

```text
dirty write       脏写
dirty read        脏读
lost update       丢失更新
unrepeatable read 不可重复读
phantom           幻读
```

同时，SS2PL 可能产生死锁，所以题目要求使用 wait-die 策略做死锁预防。wait-die 的规则是：

1. 每个事务有固定优先级。
2. 开始更早的事务优先级更高。
3. 申请锁时，如果冲突事务优先级更低，当前事务可以等待。
4. 如果冲突事务优先级更高或相同方向上当前事务更年轻，当前事务立即回滚。
5. 冲突对象不仅包括已经持有锁的事务，也包括已经在等待同一锁的事务。

题目还有一个输出约束：

1. `select` 输出格式不能改，不能修改 `src/record_printer.h`。
2. 因 wait-die 死锁预防而回滚的事务，客户端只能收到：

```text
abort
```

实际字符串为：

```text
abort\n
```

3. 除 `select` 结果和事务回滚信息外，不能向客户端返回多余信息。

因此本题实现时需要同时满足三点：

1. 并发正确性：必须避免五类数据异常。
2. 死锁预防：冲突锁申请必须按 wait-die 决策等待或回滚。
3. 输出兼容性：回滚路径必须走 `TransactionAbortException`，最终由 `rmdb.cpp` 返回精确的 `abort\n`。

## 二、总体设计

本次实现采用保守但完整的表级 SS2PL 方案。

核心策略：

```text
select              -> 表级共享锁 S
insert              -> 表级排他锁 X
update / delete     -> 收集 rid 前先拿表级排他锁 X
drop table          -> 表级排他锁 X
create / drop index -> 表级排他锁 X
commit / abort      -> 事务结束时统一释放所有锁
```

为什么选择表级锁：

1. 题面明确说明，为避免幻读，插入操作允许使用表级排他锁。
2. 只要所有读写都服从表级 `S/X` 兼容规则，就能实现冲突可串行化。
3. 当前 RMDB 框架没有完整的 gap lock 或 predicate lock，行级锁不能天然解决幻读。
4. 索引页和记录页的并发保护也不完善，表级写锁可以避免两个写事务同时修改同一张表的基表和索引结构。
5. 隐藏测试更关注隔离级别正确性，表级锁牺牲一部分并发度，但行为简单、确定、容易证明。

整体执行链路如下：

```text
客户端 SQL
  -> rmdb.cpp 为连接绑定当前事务
  -> analyze / optimizer 生成 Plan
  -> Portal 把 Plan 转成 Executor
  -> Executor 执行前申请表级锁
  -> LockManager 按兼容矩阵和 wait-die 决策
  -> DML 正常执行并记录 write_set
  -> commit / abort 时 TransactionManager 释放所有锁
```

其中事务结束前不会主动释放任何锁，这就是强严格两阶段封锁协议的关键。

6. `portal.h`：`update / delete` 收集待修改 `rid` 前构造 `WRITE` 扫描，关闭“先读后写”的并发窗口。
7. `sm_manager.cpp`：对影响已有表结构和索引结构的 DDL 申请表级 `X` 锁。

## 四、原有并发控制基础

框架中已经有事务和锁相关的数据结构，但题目八之前并没有真正实现并发控制。

### 4.1 Transaction 中已有的数据

文件：

```text
rmdb/src/transaction/transaction.h
rmdb/src/transaction/txn_defs.h
```

`Transaction` 中已经有：

```cpp
std::shared_ptr<std::deque<WriteRecord *>> write_set_;
std::shared_ptr<std::unordered_set<LockDataId>> lock_set_;
txn_id_t txn_id_;
timestamp_t start_ts_;
TransactionState state_;
```

其中：

1. `write_set_` 已经在题目七中用于事务回滚。
2. `lock_set_` 用来记录当前事务已经申请到的锁。
3. `txn_id_` 是事务唯一 ID。
4. `start_ts_` 是事务开始时间戳。
5. `state_` 用于区分 `GROWING / SHRINKING / COMMITTED / ABORTED` 等状态。

`LockDataId` 已经支持表级锁和行级锁：

```cpp
enum class LockDataType { TABLE = 0, RECORD = 1 };
```

表级锁用表文件描述符 `fd` 标识：

```text
LockDataId(fd, LockDataType::TABLE)
```

行级锁用表文件描述符加 `Rid` 标识：

```text
LockDataId(fd, rid, LockDataType::RECORD)
```

本题最终主要使用表级锁，但行锁接口也接入了同一套 `LockManager` 逻辑，方便后续扩展。

### 4.2 LockManager 原本的问题

题目八之前，`LockManager` 接口存在，但核心逻辑为空或不完整：

```text
lock_shared_on_record
lock_exclusive_on_record
lock_shared_on_table
lock_exclusive_on_table
lock_IS_on_table
lock_IX_on_table
unlock
```

如果只在事务结束时清空 `lock_set_`，不会产生任何实际并发控制效果：

```cpp
txn->get_lock_set()->clear();
```

这会带来两个问题：

1. 冲突事务不会等待，也不会按 wait-die 回滚。
2. 即使某个事务理论上“释放了锁”，等待队列也不会被唤醒。

因此本题必须补齐真正的锁队列和条件变量等待机制。

### 4.3 rmdb.cpp 已有的回滚输出入口

文件：

```text
rmdb/src/rmdb.cpp
```

服务端执行 SQL 时已经捕获事务回滚异常：

```cpp
catch (TransactionAbortException &e) {
    std::string str = "abort\n";
    memcpy(data_send, str.c_str(), str.length());
    offset = str.length();
    txn_manager->abort(context->txn_, log_manager.get());
}
```

所以 `LockManager` 遇到 wait-die 回滚时不需要直接写客户端 buffer，只需要抛出：

```cpp
TransactionAbortException(txn_id, AbortReason::DEADLOCK_PREVENTION)
```

这样可以统一保证客户端收到的是题目要求的 `abort\n`。

## 五、锁粒度为什么选表级

理论上，SS2PL 可以用行级锁、表级锁、多粒度锁或 predicate lock 实现。但本题最终选择表级锁作为主路径。

原因如下。

### 5.1 表级 S/X 已经足够保证冲突可串行化

对同一张表：

```text
读事务 -> S 锁
写事务 -> X 锁
```

兼容关系是：

```text
S 与 S 兼容
S 与 X 冲突
X 与 X 冲突
```

这意味着：

1. 多个只读事务可以并发读取同一张表。
2. 写事务执行时，不允许其他读写事务并发访问同表。
3. 一个事务第一次读到的数据，在事务结束前不会被其他事务修改。
4. 一个事务写出的未提交数据，在事务结束前不会被其他事务读到。

只要锁保持到事务结束，就能得到强严格 2PL 的隔离效果。

### 5.2 表级 X 锁直接解决幻读

幻读的典型场景是：

```sql
T1: select * from t where score > 90;
T2: insert into t values (..., 95);
T1: select * from t where score > 90;
```

如果只对 T1 第一次读到的已有行加行锁，T2 插入的新行没有被锁住，T1 第二次查询就可能多出一行。

本题中：

```text
T1 select -> 持有表级 S 锁直到事务结束
T2 insert -> 必须申请表级 X 锁
```

`S` 与 `X` 冲突，所以 T2 不能穿过 T1 的读事务完成插入，幻读被直接避免。

### 5.3 update/delete 也必须在扫描前拿写锁

`update / delete` 的执行过程分两步：

```text
先扫描条件，收集满足条件的 rid
再对这些 rid 做 update/delete
```

如果扫描时只拿读锁，甚至不拿锁，后续再拿写锁，就会留下窗口：

```text
T1 扫描得到 rid 集合
T2 插入/修改/删除同表数据
T1 根据旧 rid 集合执行写入
```

这样可能产生丢失更新或不满足谓词的修改结果。

因此本题在 `Portal` 中让 `update / delete` 的扫描阶段直接使用 `ScanLockMode::WRITE`，扫描开始时就申请表级 `X` 锁。

## 六、LockManager 数据结构

文件：

```text
rmdb/src/transaction/concurrency/lock_manager.h
```

本题补齐了 `LockManager` 中的三个核心结构：

```cpp
enum class LockMode {
    SHARED,
    EXLUCSIVE,
    INTENTION_SHARED,
    INTENTION_EXCLUSIVE,
    S_IX
};
```

这里保留了框架原有拼写 `EXLUCSIVE`，不额外改名，避免扩大修改面。

每个锁申请用 `LockRequest` 表示：

```cpp
class LockRequest {
public:
    txn_id_t txn_id_;
    LockMode lock_mode_;
    bool granted_;
    bool upgrade_;
    LockMode prev_lock_mode_;
};
```

字段含义：

1. `txn_id_`：申请锁的事务。
2. `lock_mode_`：申请的锁模式。
3. `granted_`：是否已经被授予。
4. `upgrade_`：是否是锁升级请求。
5. `prev_lock_mode_`：升级前持有的旧锁模式。

每个数据项对应一个 `LockRequestQueue`：

```cpp
class LockRequestQueue {
public:
    std::list<LockRequest> request_queue_;
    std::condition_variable cv_;
    GroupLockMode group_lock_mode_;
    std::mutex latch_;
    txn_id_t upgrading_txn_id_;
};
```

设计要点：

1. 每个 `LockDataId` 对应一个独立队列。
2. 每个队列有自己的 `mutex + condition_variable`。
3. 全局 `latch_` 只保护 `lock_table_` 的查找和创建。
4. 事务等待某个数据项上的锁时，只阻塞该数据项的队列，不阻塞整个锁表。
5. `upgrading_txn_id_` 用来保证同一数据项上最多只有一个事务正在做锁升级。

全局锁表使用：

```cpp
std::unordered_map<LockDataId, std::shared_ptr<LockRequestQueue>> lock_table_;
```

这里队列用 `shared_ptr` 保存，原因是等待线程可能正持有某个队列并在条件变量上睡眠。如果 `unlock` 时从 `lock_table_` 中删除空队列，容易引入队列生命周期问题。因此实现中只删除队列里的请求，不主动销毁锁表中的空队列。

## 七、锁兼容性矩阵

文件：

```text
rmdb/src/transaction/concurrency/lock_manager.cpp
```

锁兼容性由 `request_conflict` 实现。

本题实现的兼容矩阵如下：

```text
已持有 \ 新申请 | S   X   IS  IX  SIX
---------------|----------------------
S              | Y   N   Y   N   N
X              | N   N   N   N   N
IS             | Y   N   Y   Y   Y
IX             | N   N   Y   Y   N
SIX            | N   N   Y   N   N
```

含义：

1. `S` 可以和 `S / IS` 共存。
2. `X` 与任何其他锁都冲突。
3. `IS` 可以和 `S / IS / IX / SIX` 共存。
4. `IX` 可以和 `IS / IX` 共存。
5. `SIX` 只和 `IS` 共存。

当前执行器主路径主要使用：

```text
SHARED
EXLUCSIVE
```

也就是表级 `S / X`。但 `IS / IX / SIX` 兼容矩阵也一并实现，原因是框架接口已经暴露了多粒度锁方法，完整实现可以避免后续扩展时重写锁管理器。

## 八、wait-die 策略实现

题目规定：

```text
较早开始的事务优先级更高
```

框架中 `TransactionManager::begin` 分配事务 ID 的方式是递增：

```cpp
txn = new Transaction(next_txn_id_++);
txn->set_start_ts(next_timestamp_++);
```

因此可以使用 `txn_id` 表示优先级：

```text
txn_id 小 -> 开始更早 -> 优先级更高
txn_id 大 -> 开始更晚 -> 优先级更低
```

wait-die 决策规则实现为：

```text
申请锁事务 T
  如果存在与 T 冲突的请求 R，且 R.txn_id < T.txn_id：
      T 比冲突事务更年轻，立即回滚
  否则如果存在冲突请求：
      T 比冲突事务更老，可以等待
  否则：
      直接授予锁
```

其中冲突请求包括：

```text
已授予请求
等待中请求
```

对应实现是：

```cpp
has_conflict_with_higher_priority(...)
has_conflict_with_any(...)
```

`has_conflict_with_higher_priority` 会扫描整个 `request_queue_`，跳过当前事务和指定忽略事务，然后判断：

```text
锁模式冲突 && 对方 txn_id 更小
```

如果成立，当前事务抛出：

```cpp
TransactionAbortException(txn->get_transaction_id(),
                          AbortReason::DEADLOCK_PREVENTION)
```

典型例子：

```text
T1 txn_id = 1，已经持有 X
T2 txn_id = 2，申请 S
```

`T2` 更年轻，请求和 `T1` 冲突，所以 `T2` 立即回滚。

反过来：

```text
T2 txn_id = 2，已经持有 X
T1 txn_id = 1，申请 S
```

`T1` 更老，请求和 `T2` 冲突，所以 `T1` 等待 `T2` 结束后继续执行。

这种策略不会形成等待环。因为等待只会从老事务指向年轻事务，不可能沿着等待边回到更老事务。

## 九、lock_internal 加锁流程

所有具体加锁接口最终都走统一函数：

```cpp
bool LockManager::lock_internal(Transaction *txn,
                                const LockDataId &lock_data_id,
                                LockMode lock_mode);
```

外部接口只是构造不同的 `LockDataId` 和 `LockMode`：

```cpp
lock_shared_on_record(...)
lock_exclusive_on_record(...)
lock_shared_on_table(...)
lock_exclusive_on_table(...)
lock_IS_on_table(...)
lock_IX_on_table(...)
```

### 9.1 事务状态检查

加锁前先检查事务状态：

```text
如果 txn == nullptr:
  返回 false

如果 txn.state != GROWING:
  抛出 LOCK_ON_SHIRINKING
```

SS2PL 仍然遵循两阶段封锁：

1. `GROWING` 阶段可以申请锁。
2. 一旦进入 `SHRINKING` 阶段，就不能再申请新锁。

本题中事务只会在 `commit / abort` 释放锁前切到 `SHRINKING`，所以正常 SQL 执行期间都处于 `GROWING`。

### 9.2 已有等待请求

如果同一事务已经在该资源上有等待请求：

```text
等待该请求 granted_ 变成 true
返回 true
```

这样可以避免同一事务重复向同一个资源追加多个相同等待请求。

### 9.3 已经持有足够强的锁

如果事务已经持有该资源上的锁，先判断旧锁是否覆盖新锁：

```cpp
is_lock_covering(held_mode, request_mode)
```

例如：

```text
已经持有 X，再申请 S -> 直接成功
已经持有 X，再申请 X -> 直接成功
已经持有 S，再申请 IS -> 直接成功
```

这对执行器很重要。因为本题在多个入口加了写锁保护：

1. `update/delete` 扫描前已经通过 `Portal` 申请 `X`。
2. `UpdateExecutor / DeleteExecutor` 的 `Next()` 开头还会再申请一次 `X`。

第二次申请必须是幂等 no-op，不能错误等待或回滚。

### 9.4 锁升级

如果事务已经持有锁，但旧锁不能覆盖新锁，就进入升级逻辑。

典型场景：

```sql
begin;
select * from t;
update t set ...;
commit;
```

同一事务先对表 `t` 持有 `S`，后续写同表需要升级到 `X`。

升级规则：

1. 同一个资源只允许一个事务处于升级状态。
2. 如果已经有其他事务在升级，当前事务抛 `UPGRADE_CONFLICT`。
3. 如果没有冲突，直接把旧请求改成新锁模式。
4. 如果有冲突，继续按 wait-die 判断：
   - 存在更老的冲突事务，当前事务回滚。
   - 只存在更年轻的冲突事务，当前事务等待。
5. 等待成功后，删除旧授予请求，把升级请求标记为已授予。

设置 `upgrading_txn_id_` 的原因是避免两个事务同时从 `S` 升级到 `X` 时互相等待。

例如：

```text
T1 持有 S，想升级 X
T2 持有 S，想升级 X
```

如果不限制升级者，两个事务都持有 `S`，又都等待对方释放 `S`，会形成升级死锁。`upgrading_txn_id_` 可以让第二个升级者立即回滚。

### 9.5 新锁申请

如果事务之前没有持有该资源上的锁：

```text
检查是否有任何冲突请求
  没有冲突:
      插入请求并标记 granted = true
      加入 txn.lock_set_
      notify_all
  有冲突:
      如果存在更老的冲突请求:
          抛 DEADLOCK_PREVENTION
      否则:
          插入等待请求
          在 condition_variable 上等待
          被唤醒且与已授予请求兼容后授予锁
```

等待谓词只在锁队列互斥量保护下检查已经授予的请求，保证真正授予锁时不会和当前持锁事务冲突。

最终授予锁后：

```text
request.granted_ = true
queue.group_lock_mode_ = calc_group_lock_mode(queue)
txn.lock_set_.insert(lock_data_id)
queue.cv_.notify_all()
```

`notify_all` 的作用是唤醒同队列中的其他等待事务，让它们重新检查是否可以继续执行。

## 十、unlock 和等待唤醒

文件：

```text
rmdb/src/transaction/concurrency/lock_manager.cpp
```

`unlock` 的流程：

```text
1. 根据 LockDataId 找到锁队列。
2. 在队列 latch 保护下删除当前事务的所有请求。
3. 如果当前事务正在升级，清空 upgrading_txn_id_。
4. 重新计算 group_lock_mode_。
5. 从 txn.lock_set_ 删除该 LockDataId。
6. notify_all 唤醒等待者。
```

实现上没有在队列为空时从 `lock_table_` 中删除该队列。原因是条件变量等待依赖队列对象的生命周期，保留空队列可以避免并发删除导致等待线程访问失效对象。

`unlock` 不会直接决定下一个事务是谁，只负责释放当前事务请求并唤醒等待线程。等待线程醒来后会在自己的等待谓词中重新检查兼容性。

## 十一、执行器如何接锁

本题在执行器层接入锁，保证所有用户可见的读写路径都会进入 `LockManager`。

### 11.1 新增 ScanLockMode

文件：

```text
rmdb/src/execution/execution_defs.h
```

新增：

```cpp
enum class ScanLockMode {
    READ,
    WRITE
};
```

它用于区分扫描执行器的用途：

```text
READ  -> select 普通读扫描
WRITE -> update/delete 的写前扫描
```

### 11.2 SeqScanExecutor 加锁

文件：

```text
rmdb/src/execution/executor_seq_scan.h
```

`SeqScanExecutor` 新增字段：

```cpp
ScanLockMode lock_mode_;
bool lock_acquired_{false};
```

在 `beginTuple()` 开始扫描前：

```text
如果 lock_mode_ == READ:
    lock_shared_on_table(txn, fd)
否则:
    lock_exclusive_on_table(txn, fd)
```

`lock_acquired_` 防止同一个扫描执行器重复调用 `beginTuple()` 时重复申请锁。

### 11.3 IndexScanExecutor 加锁

文件：

```text
rmdb/src/execution/executor_index_scan.h
```

索引扫描和顺序扫描采用同样策略：

```text
READ  -> 表级 S 锁
WRITE -> 表级 X 锁
```

这里必须在索引扫描前对整张表加锁，而不是只锁索引命中的 rid。原因是：

1. 索引扫描也可能用于范围查询。
2. 范围查询有幻读风险。
3. update/delete 的索引扫描在收集 rid 前就必须排除并发写入。

### 11.4 Portal 中区分读扫描和写扫描

文件：

```text
rmdb/src/portal.h
```

`select` 仍然使用默认读扫描：

```cpp
convert_plan_executor(p, context)
```

`update / delete` 改为写扫描：

```cpp
convert_plan_executor(x->subplan_, context, ScanLockMode::WRITE)
```

然后再收集满足条件的 `rid`：

```cpp
for (scan->beginTuple(); !scan->is_end(); scan->nextTuple()) {
    rids.push_back(scan->rid());
}
```

这一步非常关键。它保证 `update / delete` 的谓词扫描和后续写入在同一个表级 `X` 锁保护下完成，不会出现扫描集合被其他事务改变的问题。

### 11.5 写执行器入口的幂等写锁

文件：

```text
rmdb/src/execution/executor_insert.h
rmdb/src/execution/executor_update.h
rmdb/src/execution/executor_delete.h
```

三个写执行器的 `Next()` 开头都申请表级 `X` 锁：

```text
InsertExecutor::Next -> lock_exclusive_on_table
UpdateExecutor::Next -> lock_exclusive_on_table
DeleteExecutor::Next -> lock_exclusive_on_table
```

其中 `insert` 没有扫描阶段，所以必须在 `InsertExecutor` 自己加锁。

`update / delete` 已经在 `Portal` 的写扫描阶段加过 `X`，这里再次加锁是防御性保护：

1. 正常路径下，`LockManager` 发现已经持有 `X`，直接返回。
2. 如果未来有其他代码绕过 `Portal` 直接调用写执行器，仍然会被并发控制保护。

## 十二、事务结束如何释放锁

文件：

```text
rmdb/src/transaction/transaction_manager.cpp
```

本题新增辅助函数：

```cpp
static void release_all_locks(TransactionManager *txn_mgr, Transaction *txn)
```

释放策略：

```text
while lock_set 非空:
    取出一个 LockDataId
    调用 lock_manager->unlock(txn, lock_data_id)
    如果 unlock 返回 false，则从 lock_set 中擦掉该项，避免死循环
```

### 12.1 commit 流程

`commit` 的最终流程是：

```text
1. 如果事务已经 COMMITTED / ABORTED，直接返回。
2. 清理 write_set_，不撤销任何数据。
3. flush log。
4. 将事务状态切到 SHRINKING。
5. release_all_locks 释放所有锁。
6. 清空 lock_set_。
7. 将事务状态切到 COMMITTED。
```

为什么释放锁前先切到 `SHRINKING`：

1. 两阶段封锁要求释放锁后不能再申请新锁。
2. 状态切换能阻止异常路径在释放阶段重新申请锁。

### 12.2 abort 流程

`abort` 的最终流程是：

```text
1. 如果事务已经 COMMITTED / ABORTED，直接返回。
2. 逆序遍历 write_set_。
3. 对 INSERT_TUPLE 删除插入记录并删除索引项。
4. 对 DELETE_TUPLE 恢复旧记录并恢复索引项。
5. 对 UPDATE_TUPLE 恢复旧记录，并在索引 key 改变时恢复索引项。
6. flush log。
7. 将事务状态切到 SHRINKING。
8. release_all_locks 释放所有锁。
9. 清空 lock_set_。
10. 将事务状态切到 ABORTED。
```

这里必须先 undo，再释放锁。

如果先释放锁，再回滚数据，就可能出现：

```text
T1 abort 已释放 X 锁，但旧数据还没恢复
T2 select 获得 S 锁，读到 T1 的未回滚中间状态
```

这会破坏 strict 2PL。当前实现先完成回滚，再释放锁，所以其他事务看不到未提交写入，也看不到回滚过程中的中间状态。

## 十三、DDL 如何加锁

文件：

```text
rmdb/src/system/sm_manager.cpp
```

本题对影响已有表资源的 DDL 加表级 `X` 锁：

```text
drop table
create index
drop index
```

原因：

1. `drop table` 会关闭并销毁表文件和索引文件，必须排斥并发读写。
2. `create index` 会扫描已有表记录并创建索引项，不能和并发写入交错。
3. `drop index` 会删除索引元数据和索引文件，不能和并发查询或写入索引交错。

`create table` 不加锁，因为它创建的是一个新表，之前不存在对应表资源，也不存在对该表的并发读写。

## 十四、五类数据异常如何避免

本题的核心验证就是五类异常。下面逐一说明当前实现为什么能避免。

### 14.1 脏写 dirty write

脏写是两个事务同时写同一数据项，其中一个事务覆盖了另一个未提交事务的写入。

本实现中：

```text
insert/update/delete -> 表级 X 锁
```

两个写事务访问同一张表时都需要 `X` 锁，而 `X` 与 `X` 冲突。

因此：

1. 如果老事务申请年轻事务持有的 `X`，老事务等待。
2. 如果年轻事务申请老事务持有的 `X`，年轻事务回滚。
3. 不会出现两个写事务同时修改同一张表的情况。

所以脏写被避免。

### 14.2 脏读 dirty read

脏读是一个事务读到了另一个事务尚未提交的写入。

本实现中：

```text
写事务 update -> 持有表级 X 锁直到 commit/abort
读事务 select -> 需要表级 S 锁
S 与 X 冲突
```

因此读事务不可能在写事务未结束时读到写事务的中间结果。

如果写事务最后 `abort`：

1. `TransactionManager::abort` 先根据 `write_set_` 恢复旧记录和索引。
2. 然后释放 `X` 锁。
3. 等待中的读事务获得 `S` 锁后，只能读到回滚后的旧值。

### 14.3 丢失更新 lost update

丢失更新的典型场景：

```text
T1 read x = 10
T2 read x = 10
T1 update x = 11
T2 update x = 12
```

最后 `T1` 的更新被覆盖。

本实现中，`update` 在扫描待修改记录前就持有表级 `X` 锁：

```text
Portal -> WRITE scan -> lock_exclusive_on_table
```

所以同一张表上不会有两个 `update` 并发完成读-改-写序列。第二个事务只能等待或按 wait-die 回滚。

### 14.4 不可重复读 unrepeatable read

不可重复读是同一事务两次读取同一条件，期间其他事务修改了数据，导致两次结果不一致。

本实现中：

```text
第一次 select -> 获得表级 S 锁
锁直到 commit/abort 才释放
其他 update/delete -> 需要表级 X 锁
```

只要读事务没有结束，其他写事务就不能修改这张表。

因此同一事务内第二次 `select` 不会看到中途被其他事务修改后的结果。

### 14.5 幻读 phantom

幻读是同一事务两次按条件范围查询，第二次多出或少了满足条件的记录。

本实现中：

```text
select -> 表级 S 锁
insert -> 表级 X 锁
delete -> 表级 X 锁
update -> 表级 X 锁
```

读事务持有 `S` 期间，其他事务无法插入、删除或修改同表记录，所以满足谓词的记录集合不会变化。

因此幻读被避免。

## 十五、题面脏读样例执行过程

题面给出的并发调度是：

```text
t2a t1a t1b t2b t1c t2c t3a
```

初始数据：

```sql
create table concurrency_test (id int, name char(8), score float);
insert into concurrency_test values (1, 'xiaohong', 90.0);
insert into concurrency_test values (2, 'xiaoming', 95.0);
insert into concurrency_test values (3, 'zhanghua', 88.5);
```

事务：

```text
T1:
  begin;
  update concurrency_test set score = 100.0 where id = 2;
  abort;

T2:
  begin;
  select * from concurrency_test where id = 2;
  commit;

T3:
  select * from concurrency_test where id = 2;
```

具体执行过程：

### 15.1 t2a begin

T2 先开始，因此：

```text
T2 txn_id 更小
T2 优先级更高
T2 状态为 GROWING
```

此时 T2 还没有执行查询，所以暂时没有锁。

### 15.2 t1a begin

T1 后开始：

```text
T1 txn_id 更大
T1 优先级低于 T2
T1 状态为 GROWING
```

### 15.3 t1b update

T1 执行：

```sql
update concurrency_test set score = 100.0 where id = 2;
```

`Portal` 为 update 构造 `WRITE` 扫描：

```text
SeqScan/IndexScan beginTuple
  -> lock_exclusive_on_table(T1)
```

此时 T2 虽然更老，但还没有持有该表的锁，所以 T1 可以获得表级 `X` 锁并执行更新。

更新后：

```text
id = 2 的 score 临时变成 100.0
T1 write_set_ 记录 UPDATE_TUPLE，保存旧记录 score = 95.0
T1 持有表级 X 锁，不释放
```

### 15.4 t2b select

T2 执行：

```sql
select * from concurrency_test where id = 2;
```

扫描执行器申请表级 `S` 锁：

```text
T2 申请 S
T1 持有 X
S 与 X 冲突
```

wait-die 判断：

```text
T2 txn_id 更小，优先级高于 T1
```

因此 T2 不回滚，而是等待 T1 释放 `X` 锁。

这一步是题面样例的关键。如果没有 SS2PL，T2 会直接读到 T1 未提交的 `100.0`，产生脏读。

### 15.5 t1c abort

T1 回滚：

```text
TransactionManager::abort(T1)
  -> 根据 UPDATE_TUPLE 恢复旧记录 score = 95.0
  -> 恢复相关索引项
  -> 状态切到 SHRINKING
  -> unlock 表级 X 锁
  -> 状态切到 ABORTED
```

释放锁后，`LockManager::unlock` 调用 `notify_all` 唤醒等待在同一锁队列上的 T2。

### 15.6 t2b 继续 select

T2 被唤醒后重新检查兼容性。

此时 T1 的 `X` 锁已经释放，T2 获得表级 `S` 锁，然后读取记录：

```text
id = 2
name = xiaoming
score = 95.000000
```

也就是回滚后的旧值，而不是 T1 未提交的 `100.0`。

### 15.7 t2c commit

T2 提交：

```text
清理 write_set_
状态切到 SHRINKING
释放表级 S 锁
状态切到 COMMITTED
```

### 15.8 t3a select

T3 是单条隐式事务：

```text
SetTransaction 创建新事务
select 申请表级 S 锁
读取 id = 2
语句结束后自动 commit 并释放 S 锁
```

T3 也读到：

```text
score = 95.000000
```

所以题面期望的两次输出都能满足。

## 十六、wait-die 边界场景

### 16.1 年轻事务遇到老事务

场景：

```text
T1 先 begin，持有 X
T2 后 begin，申请 S
```

结果：

```text
T2 发现冲突请求 T1 的 txn_id 更小
T2 抛 DEADLOCK_PREVENTION
客户端收到 abort\n
```

这验证了 wait-die 的 die 分支。

### 16.2 老事务遇到年轻事务

场景：

```text
T2 后 begin，持有 X
T1 先 begin，申请 S
```

结果：

```text
T1 优先级更高
T1 等待 T2 释放锁
T2 commit/abort 后 T1 继续执行
```

这验证了 wait-die 的 wait 分支。

### 16.3 等待队列中的请求也参与判断

题目明确要求：

```text
持有该锁或已经在等待该锁的事务
```

所以 `has_conflict_with_higher_priority` 和 `has_conflict_with_any` 都扫描整个 `request_queue_`，不是只看 `granted_ == true` 的请求。

这样做可以避免年轻事务排在等待队列中时，后来的更年轻事务继续进入等待并形成复杂等待关系。

### 16.4 锁升级冲突

场景：

```text
T1 持有 S，准备升级 X
T2 持有 S，也准备升级 X
```

处理：

```text
第一个升级者写入 upgrading_txn_id_
第二个升级者发现已有升级事务
第二个升级者抛 UPGRADE_CONFLICT
```

这避免了多个升级者互相等待。

### 16.5 同一事务重复申请锁

场景：

```text
update/delete 的 Portal 写扫描已经申请 X
UpdateExecutor/DeleteExecutor::Next 又申请 X
```

处理：

```text
LockManager 发现当前事务已经持有 X
is_lock_covering 返回 true
直接成功
```

这样可以同时保证代码健壮性和加锁入口完整性。

## 十七、输出路径和自动提交边界

本题对输出非常敏感，因为平台通过客户端收到的字符串判定结果。

### 17.1 回滚输出

wait-die 导致的回滚不直接在 `LockManager` 中写客户端 buffer，而是抛出：

```cpp
TransactionAbortException(..., AbortReason::DEADLOCK_PREVENTION)
```

`rmdb.cpp` 捕获后统一返回：

```text
abort\n
```

服务端可以在控制台打印异常说明，但客户端不会收到这些调试信息。

### 17.2 select 输出

`select` 仍然通过原来的 `RecordPrinter` 输出，没有修改：

```text
rmdb/src/record_printer.h
```

这保证格式和平台期望一致。

### 17.3 隐式事务自动提交

单条非显式事务语句仍然使用自动事务：

```text
执行前 SetTransaction 创建事务
执行 SQL
如果 txn_mode == false 且事务未结束
  自动 commit
```

这对题目八也很重要。单条 `select` 会在语句结束后释放 `S` 锁，单条 `insert/update/delete` 会在语句结束后释放 `X` 锁，不会把锁意外保留到连接后续语句。

显式事务中：

```sql
begin;
...
commit;
```

`txn_mode == true`，每条 SQL 后不会自动提交，锁会一直保留到显式 `commit / abort`。

## 十八、实现日志

本题实现过程按以下顺序推进。

### 18.1 先确认前置能力

先检查题目三和题目七的结果：

1. 唯一索引已经能创建、删除、查询、维护。
2. DML 写执行器已经能记录 `write_set_`。
3. `abort` 已经能逆序恢复基表和索引。
4. `rmdb.cpp` 已经能区分显式事务和隐式事务。

因此题目八没有重写事务回滚，而是在现有事务框架外补并发控制。

### 18.2 补 LockManager

实现内容：

1. 为每个 `LockDataId` 建立锁请求队列。
2. 补齐 `S / X / IS / IX / SIX` 兼容性判断。
3. 用 `condition_variable` 支持老事务等待年轻事务。
4. 用 `TransactionAbortException` 支持年轻事务遇到老事务时立即回滚。
5. 支持同一事务重复申请已有锁时直接成功。
6. 支持锁升级和升级冲突检测。
7. `unlock` 删除请求并唤醒等待事务。

### 18.3 再接执行器入口

实现内容：

1. 新增 `ScanLockMode`。
2. 顺序扫描和索引扫描在 `beginTuple()` 加锁。
3. `select` 使用 `READ` 扫描。
4. `update/delete` 使用 `WRITE` 扫描。
5. `insert/update/delete` 执行器入口统一申请表级 `X` 锁。

这里重点修正的是 `update/delete`：

```text
必须在收集 rid 前加 X 锁
```

否则即使最终写入时加锁，也已经无法保证谓词扫描结果稳定。

### 18.4 然后修事务结束释放锁

实现内容：

1. 新增 `release_all_locks`。
2. `commit` 清理写集后释放锁。
3. `abort` 完成 undo 后释放锁。
4. 释放锁时通过 `LockManager::unlock` 唤醒等待事务。

这里重点是：

```text
不能只 clear lock_set_
```

因为 `clear` 不会修改锁队列，也不会唤醒等待事务。

### 18.5 最后补 DDL 锁

实现内容：

1. `drop table` 加表级 `X`。
2. `create index` 加表级 `X`。
3. `drop index` 加表级 `X`。
4. `create table` 不加锁，因为没有已有表资源。

这样 DML 和 DDL 不会交错破坏表文件、索引文件和元数据。

## 二十、关键边界总结

本实现中最容易出错的边界如下。

### 20.1 只在写入时加 X 锁是不够的

`update/delete` 必须在扫描前加 `X` 锁。

否则：

```text
扫描 rid 集合
其他事务修改表
再写旧 rid 集合
```

会产生并发窗口。

### 20.2 abort 必须先 undo 再 unlock

如果先释放锁，再回滚数据，等待事务可能读到尚未恢复的数据。

当前顺序是：

```text
undo write_set_
set SHRINKING
unlock all
set ABORTED
```

符合 strict 2PL。

### 20.3 wait-die 不能只看已授予锁

题目要求等待中的冲突事务也参与优先级比较。

当前实现扫描整个锁请求队列，因此不会漏掉已经在等待同一资源的冲突请求。

### 20.4 DML 执行器重复加锁必须幂等

同一事务可能通过多个入口申请同一张表的 `X` 锁。

当前实现用 `is_lock_covering` 判断已有锁是否足够强，避免重复申请造成自冲突。

### 20.5 不能直接清空 lock_set_

`lock_set_` 只是事务侧记录，不是锁管理器的真实队列。

只有调用：

```cpp
lock_manager->unlock(txn, lock_data_id)
```

才能从资源队列中删除请求并唤醒等待事务。

## 二十一、结论

题目八最终实现的是一套完整的表级强严格两阶段封锁协议：

```text
读操作持有表级 S 锁
写操作持有表级 X 锁
锁保持到 commit/abort
wait-die 决定等待或回滚
事务结束统一 unlock 并唤醒等待者
```

该设计虽然比行级锁保守，但能完整满足本题的正确性要求：

1. 避免脏写。
2. 避免脏读。
3. 避免丢失更新。
4. 避免不可重复读。
5. 避免幻读。
6. 避免死锁。
7. 保持客户端输出格式符合平台要求。

最终平台测试结果为 `all passed`。
