# 题目七：事务控制

本文档说明题目七“事务控制”的实现方式。内容主要为：
本次修改的目标、
涉及文件、
每个模块修改逻辑、
`begin / commit / abort` 的执行流程、
写集回滚策略、
索引一致性维护、
本地验证方式。

本题建立在前序题目的能力之上：
1. 题目二已经打通 `insert / delete / update / select` 的基本执行链路。
2. 题目三已经实现唯一索引，以及 DML 执行时对索引的同步维护。
3. 本题需要让多条 DML 在显式事务中作为一个整体提交或回滚，并且在有索引和无索引两种情况下都保持基表和索引一致。

## 一、题目要求分析

系统需要支持三条显式事务控制语句：

```sql
begin;
commit;
abort;
```

显式事务中只包含：

```sql
insert
delete
update
select
```

不包含 DDL 语句。本题测试数据不包含并发事务，并发事务将作为后续题目重点，因此这里我们实现的重点不是锁冲突和调度，而是一下这几点：

1. `begin` 后的多条 DML 不能每条自动提交。
2. `commit` 后保留本事务内所有写入结果。
3. `abort` 后撤销本事务内所有写入结果。
4. 回滚时不仅要恢复表记录，还要恢复唯一索引。
5. 单条非显式事务语句仍保持原框架的自动事务行为。

典型测试：

```sql
create table student (id int, name char(8), score float);
insert into student values (1, 'xiaohong', 90.0);

begin;
insert into student values (2, 'xiaoming', 99.0);
delete from student where id = 2;
abort;

select * from student;
```

期望只剩第一条记录：

```text
| id | name | score |
| 1 | xiaohong | 90.000000 |
```

## 二、总体设计

本题的核心设计是使用 `Transaction` 中已有的写集 `write_set_` 保存每条写操作的反向恢复信息。

执行 DML 时：

```text
insert -> 记录插入后的 rid
delete -> 记录删除前的旧 tuple
update -> 记录更新前的旧 tuple
```

执行 `commit` 时：

```text
不撤销任何数据
清理 write_set
标记事务 COMMITTED
```

执行 `abort` 时：

```text
按 write_set 的逆序逐条回滚
恢复表记录
恢复索引项
清理 write_set
标记事务 ABORTED
```

为什么必须逆序回滚：

一个事务内同一条记录可能经历多次修改。例如：

```sql
begin;
insert into t values (1, 10);
update t set v = 20 where id = 1;
delete from t where id = 1;
abort;
```

如果按正序回滚，会先撤销插入，后续 update/delete 的反向操作就找不到正确状态。逆序回滚符合栈式 undo 逻辑，可以从当前状态一步步退回事务开始前的状态。

## 五、写集数据结构的使用

文件：

```text
rmdb/src/transaction/transaction.h
rmdb/src/transaction/txn_defs.h
```

框架中 `Transaction` 已经包含：

```cpp
std::shared_ptr<std::deque<WriteRecord *>> write_set_;
```

`WriteRecord` 支持三类写操作：

```cpp
enum class WType {
    INSERT_TUPLE = 0,
    DELETE_TUPLE,
    UPDATE_TUPLE
};
```

记录内容：

1. `INSERT_TUPLE`：保存表名和插入后的 `Rid`。
2. `DELETE_TUPLE`：保存表名、被删除记录的 `Rid`、删除前的完整 `RmRecord`。
3. `UPDATE_TUPLE`：保存表名、被更新记录的 `Rid`、更新前的完整 `RmRecord`。

本题直接复用这套结构，不新增另一套日志格式。原因是本题不要求崩溃恢复和并发事务，只要求当前进程内的显式事务能正确提交和回滚。

## 六、统一索引 key 构造

文件：

```text
rmdb/src/execution/execution_defs.h
```

新增函数：

```cpp
inline std::vector<char> make_index_key(const IndexMeta &index, const RmRecord &rec) {
    std::vector<char> key(index.col_tot_len);
    int offset = 0;
    for (auto &col : index.cols) {
        memcpy(key.data() + offset, rec.data + col.offset, col.len);
        offset += col.len;
    }
    return key;
}
```

为什么要抽成公共函数：

1. `delete`、`update`、`abort` 都需要从记录中拼出复合索引 key。
2. 复合索引 key 的布局必须和题目三保持一致，即按 `IndexMeta::cols` 的顺序，把各列原始字节连续拼接。
3. 如果每个地方手写一遍，后续很容易出现偏移、长度、列顺序不一致，导致索引删除或恢复失败。

这个函数只负责根据索引元数据从一条 `RmRecord` 中取出 key，不改变记录，也不访问索引文件。

## 七、InsertExecutor 怎么改

文件：

```text
rmdb/src/execution/executor_insert.h
```

插入执行流程调整为：

```text
1. 根据 values 构造完整 RmRecord
2. 对所有唯一索引预先检查重复 key
3. 插入表记录，得到 rid
4. 向当前事务追加 INSERT_TUPLE 写记录
5. 向所有索引插入 key -> rid
```

新增关键逻辑：

```cpp
rid_ = fh_->insert_record(rec.data, context_);
if (context_ != nullptr && context_->txn_ != nullptr) {
    context_->txn_->append_write_record(new WriteRecord(WType::INSERT_TUPLE, tab_name_, rid_));
}
```

为什么 `INSERT_TUPLE` 只需要保存 `Rid`：

插入操作的回滚动作是“把刚插入的记录删掉”。当前记录内容仍然在表文件中，回滚时可以用 `Rid` 找到它，并据此删除索引项。

为什么先检查唯一索引再写表：

如果插入 key 已经存在，应该直接报错，不应该污染表文件和写集。这个行为延续题目三的唯一索引实现。

## 八、DeleteExecutor 怎么改

文件：

```text
rmdb/src/execution/executor_delete.h
```

删除执行流程调整为：

```text
1. 根据 rid 读取删除前记录 old_rec
2. 删除该记录对应的所有索引项
3. 向当前事务追加 DELETE_TUPLE 写记录，保存 old_rec
4. 删除表记录
```

新增关键逻辑：

```cpp
auto rec = fh_->get_record(rid, context_);
for (auto &index : tab_.indexes) {
    auto ih = sm_manager_->ihs_.at(sm_manager_->get_ix_manager()->get_index_name(tab_name_, index.cols)).get();
    auto key = make_index_key(index, *rec);
    ih->delete_entry(key.data(), context_->txn_);
}
if (context_ != nullptr && context_->txn_ != nullptr) {
    context_->txn_->append_write_record(new WriteRecord(WType::DELETE_TUPLE, tab_name_, rid, *rec));
}
fh_->delete_record(rid, context_);
```

为什么 `DELETE_TUPLE` 必须保存完整旧记录：

删除后，表文件中对应 slot 已经不可见。回滚时如果只保存 `Rid`，无法恢复原始列值，也无法重新构造索引 key。因此删除前必须保存完整 `RmRecord`。

为什么删除索引用 `make_index_key`：

删除索引项需要用旧记录中的索引列值。对于复合索引，必须按索引列定义顺序拼接，否则无法命中 B+ 树中的原 key。

## 九、UpdateExecutor 怎么改

文件：

```text
rmdb/src/execution/executor_update.h
```

更新执行流程调整为：

```text
1. 根据 rid 读取更新前记录 old_rec
2. 拷贝 old_rec 生成 new_rec
3. 应用 set 子句生成更新后记录
4. 对每个索引分别构造 old_key 和 new_key
5. 只有 key 发生变化时才检查唯一性并更新索引
6. 向当前事务追加 UPDATE_TUPLE 写记录，保存 old_rec
7. 更新表记录
```

核心逻辑：

```cpp
auto old_key = make_index_key(index, *old_rec);
auto new_key = make_index_key(index, new_rec);
if (memcmp(old_key.data(), new_key.data(), index.col_tot_len) != 0) {
    std::vector<Rid> existed;
    if (ih->get_value(new_key.data(), &existed, context_->txn_) && existed[0] != rid) {
        throw InternalError("Duplicate key violates unique index");
    }
    ih->delete_entry(old_key.data(), context_->txn_);
    ih->insert_entry(new_key.data(), rid, context_->txn_);
}
```

写集记录：

```cpp
if (context_ != nullptr && context_->txn_ != nullptr) {
    context_->txn_->append_write_record(new WriteRecord(WType::UPDATE_TUPLE, tab_name_, rid, *old_rec));
}
fh_->update_record(rid, new_rec.data, context_);
```

为什么只在索引 key 改变时更新索引：

如果更新的列不属于某个索引，旧 key 和新 key 完全相同。此时删除再插入同一个 key 没有必要，还会增加索引层异常风险。尤其是唯一索引中，同一个 `rid` 对应同一个 key，不变更时保持原索引项即可。

为什么 `UPDATE_TUPLE` 保存旧记录：

更新回滚需要把当前记录恢复成更新前状态。旧记录同时还能提供旧索引 key，用于把索引从新 key 修回旧 key。

## 十、commit 怎么实现

文件：

```text
rmdb/src/transaction/transaction_manager.cpp
```

`commit` 的语义是确认事务内所有写入，不需要撤销任何表记录或索引项。

实现流程：

```text
1. 如果 txn 为空，或者已经 COMMITTED / ABORTED，直接返回
2. 删除 write_set 中保存的 WriteRecord 对象
3. 清空 lock_set
4. 刷日志
5. 设置事务状态为 COMMITTED
```

关键代码：

```cpp
auto write_set = txn->get_write_set();
while (!write_set->empty()) {
    delete write_set->back();
    write_set->pop_back();
}
txn->get_lock_set()->clear();
if (log_manager != nullptr) {
    log_manager->flush_log_to_disk();
}
txn->set_state(TransactionState::COMMITTED);
```

为什么 commit 要清理写集：

事务已经提交后，这些 undo 信息不再需要。如果不清理，长事务或大量 DML 会造成内存泄漏。

为什么要判断已提交或已回滚：

事务控制语句执行完后，外层 `rmdb.cpp` 还有自动提交逻辑。加上状态判断后，重复调用 `commit` 或 `abort` 不会再次处理已经结束的事务。

## 十一、abort 怎么实现

文件：

```text
rmdb/src/transaction/transaction_manager.cpp
```

`abort` 是本题最核心的部分。实现策略是：

```text
从 write_set 尾部开始弹出
根据写操作类型执行反向操作
每处理一条就 delete 对应 WriteRecord
最后清空锁集合并标记 ABORTED
```

### 11.1 回滚 INSERT_TUPLE

原操作：

```text
insert 一条新记录
插入对应索引项
```

回滚动作：

```text
1. 根据 rid 读取当前记录
2. 根据当前记录构造每个索引 key
3. 删除所有索引项
4. 删除表记录
```

代码逻辑：

```cpp
auto rec = fh->get_record(rid, nullptr);
for (auto &index : tab.indexes) {
    auto ih = sm_manager_->ihs_.at(sm_manager_->get_ix_manager()->get_index_name(tab_name, index.cols)).get();
    auto key = make_index_key(index, *rec);
    ih->delete_entry(key.data(), txn);
}
fh->delete_record(rid, nullptr);
```

为什么先删索引再删表记录：

索引 key 来自当前表记录。如果先删表，再想构造索引 key 就必须额外保存插入记录内容。当前设计只保存 `Rid`，所以回滚插入时先读取记录并删除索引，再删除表记录。

### 11.2 回滚 DELETE_TUPLE

原操作：

```text
删除索引项
删除表记录
```

回滚动作：

```text
1. 用保存的 old_rec 插回原 rid
2. 根据 old_rec 构造索引 key
3. 恢复所有索引项
```

代码逻辑：

```cpp
RmRecord &old_rec = write_record->GetRecord();
fh->insert_record(rid, old_rec.data);
for (auto &index : tab.indexes) {
    auto ih = sm_manager_->ihs_.at(sm_manager_->get_ix_manager()->get_index_name(tab_name, index.cols)).get();
    auto key = make_index_key(index, old_rec);
    ih->insert_entry(key.data(), rid, txn);
}
```

为什么使用 `insert_record(rid, old_rec.data)`：

回滚删除必须恢复到原来的物理位置。之前扫描器、索引项和记录管理都以 `Rid` 标识 tuple，如果恢复到新位置，索引和后续操作会失去一致性。

### 11.3 回滚 UPDATE_TUPLE

原操作：

```text
可能删除旧索引项
可能插入新索引项
更新表记录
```

回滚动作：

```text
1. 读取当前记录 curr_rec
2. 拿出写集中保存的 old_rec
3. 对每个索引构造 curr_key 和 old_key
4. 如果 key 不同，删除当前 key，插回旧 key
5. 把表记录恢复为 old_rec
```

代码逻辑：

```cpp
auto curr_rec = fh->get_record(rid, nullptr);
RmRecord &old_rec = write_record->GetRecord();
for (auto &index : tab.indexes) {
    auto ih = sm_manager_->ihs_.at(sm_manager_->get_ix_manager()->get_index_name(tab_name, index.cols)).get();
    auto curr_key = make_index_key(index, *curr_rec);
    auto old_key = make_index_key(index, old_rec);
    if (memcmp(curr_key.data(), old_key.data(), index.col_tot_len) != 0) {
        ih->delete_entry(curr_key.data(), txn);
        ih->insert_entry(old_key.data(), rid, txn);
    }
}
fh->update_record(rid, old_rec.data, nullptr);
```

为什么比较 key 后再改索引：

如果某次 update 只修改非索引列，当前索引 key 和旧索引 key 相同，不需要对索引做任何操作。这样可以保持和 `UpdateExecutor` 的正向逻辑一致。

## 十二、自动提交边界怎么修正

文件：

```text
rmdb/src/rmdb.cpp
```

框架中每条 SQL 执行前都会通过 `SetTransaction` 取得事务对象：

```text
如果当前 txn 不存在，或者已经 COMMITTED / ABORTED，就 begin 一个新事务
```

单条非显式事务语句执行后，框架会自动提交：

```cpp
if(context->txn_->get_txn_mode() == false) {
    txn_manager->commit(context->txn_, context->log_mgr_);
}
```

本题把自动提交条件收紧为：

```cpp
if(context->txn_ != nullptr && context->txn_->get_txn_mode() == false &&
   context->txn_->get_state() != TransactionState::COMMITTED &&
   context->txn_->get_state() != TransactionState::ABORTED)
{
    txn_manager->commit(context->txn_, context->log_mgr_);
}
```

为什么需要这个保护：

1. `commit;` 或 `abort;` 本身会在 `run_cmd_utility` 中结束事务。
2. 如果外层自动提交再次处理同一个事务，会造成状态重复处理。
3. 对已经结束的事务直接跳过，可以让事务边界更清晰。

显式事务内的 DML 不会自动提交，因为 `begin;` 会把当前事务设置为：

```cpp
txn_mode = true
```

后续语句复用同一个事务，直到 `commit;` 或 `abort;`。

## 十三、索引一致性为什么是本题重点

本题测试点包含“有索引”和“无索引”两类场景。有索引时，如果只回滚表记录，不回滚索引，会出现这些错误：

1. `abort` 后表中没有插入记录，但索引中还残留 key，后续插入同 key 会误报唯一冲突。
2. `abort` 后表中恢复了删除记录，但索引中没有对应 key，索引扫描查不到这条记录。
3. `abort` 后表记录恢复为旧值，但索引还指向新 key，条件查询结果错误。

因此每类写操作的 undo 都必须同时处理：

```text
基表记录
所有相关索引项
```

本题中 `make_index_key` 的存在就是为了保证正向执行器和回滚逻辑使用同一套 key 生成规则。

## 十四、为什么不重做并发控制

题目明确说明：

```text
不需要考虑并发事务的执行
测试数据中不包含并发事务
```

因此本次实现没有扩展锁管理器，也没有实现死锁检测或隔离级别细节。`commit` 和 `abort` 中只清理已有 `lock_set`，保持接口完整。

这个选择和题目范围一致：

1. 当前目标是事务原子性，不是并发隔离性。
2. 框架已有 `LockManager` 和事务状态字段，后续并发题可以继续扩展。
3. 不把并发逻辑混入本题，可以降低对查询执行、索引和记录模块的影响。

## 十五、CMake 修正

文件：

```text
rmdb/src/record/CMakeLists.txt
```

新增：

```cmake
target_link_libraries(records system transaction system storage)
```

原因：

`records` 是 `record` 模块的 shared library 目标。本地 macOS 构建时，shared library 对依赖符号解析更严格。如果只给 static library `record` 链接依赖，而不给 `records` 链接依赖，会出现构建环境相关的链接问题。

这个修改不改变事务语义，只保证本地和评测环境构建更稳定。

## 十六、完整执行过程示例

以题目样例为例：

```sql
insert into student values (1, 'xiaohong', 90.0);
begin;
insert into student values (2, 'xiaoming', 99.0);
delete from student where id = 2;
abort;
select * from student;
```

执行过程：

### 16.1 第一条 insert

这是一条普通单语句事务：

```text
SetTransaction 创建 txn0
InsertExecutor 插入 id=1
追加 INSERT_TUPLE
语句结束后自动 commit
commit 清理 txn0 写集
```

结果：`id=1` 被永久保留。

### 16.2 begin

```text
SetTransaction 创建 txn1
run_cmd_utility 设置 txn1.txn_mode = true
```

后续 SQL 复用 `txn1`，不会单条自动提交。

### 16.3 显式事务内 insert

```text
插入 id=2
追加 INSERT_TUPLE(student, rid2)
如果有索引，同时插入索引项 key(2) -> rid2
```

### 16.4 显式事务内 delete

```text
读取 rid2 对应记录 old_rec(id=2)
删除索引项 key(2)
追加 DELETE_TUPLE(student, rid2, old_rec)
删除表记录 rid2
```

此时写集顺序为：

```text
INSERT_TUPLE(id=2)
DELETE_TUPLE(id=2)
```

### 16.5 abort

逆序回滚：

```text
先回滚 DELETE_TUPLE:
  把 id=2 插回 rid2
  恢复索引 key(2) -> rid2

再回滚 INSERT_TUPLE:
  读取 rid2 当前记录
  删除索引 key(2)
  删除表记录 rid2
```

最终效果：

```text
显式事务开始前不存在 id=2
abort 后仍不存在 id=2
id=1 不受影响
```

## 十八、关键边界

### 18.1 同一事务内插入后删除再回滚

场景：

```sql
begin;
insert into t values (1);
delete from t where id = 1;
abort;
```

期望：事务开始前没有该记录，回滚后也没有。

依赖点：逆序回滚。

### 18.2 删除已有记录后回滚

场景：

```sql
insert into t values (1);
begin;
delete from t where id = 1;
abort;
```

期望：记录恢复，索引恢复。

依赖点：`DELETE_TUPLE` 保存完整旧记录。

### 18.3 更新索引列后回滚

场景：

```sql
create index t(id);
insert into t values (1, 10);
begin;
update t set id = 2 where id = 1;
abort;
select * from t where id = 1;
```

期望：可以通过索引查到 `id=1`。

依赖点：`UPDATE_TUPLE` 回滚时删除当前 key，插回旧 key。

### 18.4 更新非索引列后回滚

场景：

```sql
create index t(id);
insert into t values (1, 10);
begin;
update t set v = 20 where id = 1;
abort;
```

期望：索引不被无意义删除重插，表记录恢复为 `v=10`。

依赖点：`memcmp(old_key, new_key)` 判断 key 是否变化。

## 十九、结论

本题最终实现了一条完整的显式事务链路：

```text
begin
  标记当前事务为显式事务

DML
  正常执行表和索引修改
  同时写入 undo 所需的 WriteRecord

commit
  保留修改
  清理写集
  标记 COMMITTED

abort
  逆序读取写集
  恢复表记录
  恢复索引项
  标记 ABORTED
```

实现重点不是新增一套事务框架，而是把原框架已有的事务对象、写集、DML 执行器和索引维护逻辑连接起来，使显式事务在有索引和无索引两类测试中都满足原子性要求。
