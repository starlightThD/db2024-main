# 题目三：唯一索引详解

题目三要求在题目二查询执行的基础上支持唯一索引。它不是只要求能解析 `create index` 和 `drop index`，还要求索引真正参与查询，并且在插入、删除、更新基表记录时同步维护索引。

本次实现围绕四条主线展开：

1. 补齐 B+ 树索引文件的查找、插入、范围扫描能力。
2. 实现 `show index from table_name` 的解析、计划和输出。
3. 修改优化器，使它能按照最左匹配原则选择索引。
4. 修改 DML 执行器，使索引和基表保持同步，并检查唯一性。

## 一、题目三要实现什么

### 1. 创建、删除、展示索引

题目要求支持：

```sql
create index warehouse(id);
create index warehouse(id,name);
drop index warehouse(id);
drop index warehouse(id,name);
show index from warehouse;
```

其中 `show index from warehouse` 的输出格式为：

```text
| warehouse | unique | (id) |
| warehouse | unique | (id,name) |
```

这里的 `unique` 是固定输出，因为本题所有索引都是唯一索引。

### 2. 使用索引查询

题目要求索引不仅存在，还要真正用于查询。尤其是联合索引要支持最左匹配原则。

假设有联合索引：

```sql
create index A(id,name,score);
```

那么下面这些条件都应该可以用这个索引：

```sql
where id = 1 and name = 'abcd' and score = 99.0
where id = 1 and name = 'abcd' and score > 90.0
where id = 1 and name = 'abcd'
where name = 'abcd' and id = 1
where id = 1
where id > 1
```

核心判断规则是：

1. 从索引第一列开始匹配。
2. 等值条件可以继续向后匹配。
3. 遇到第一个范围条件后停止继续使用后续索引列。
4. where 条件顺序不重要，优化器要自己找到对应列。
5. 索引扫描后仍然用完整 where 条件过滤，保证结果正确。

### 3. 维护索引

当表上有索引时：

1. 插入记录时，要向每个索引插入对应 key 到 rid 的映射。
2. 删除记录时，要从每个索引中删除对应 key。
3. 更新记录时，要先删除旧 key，再插入新 key。
4. 对唯一索引，要在插入新 key 前检查是否已经存在。

如果只更新基表、不更新索引，后续索引查询会查到旧数据或者查不到新数据，所以这部分是题目三的关键。

## 三、B+ 树索引模块怎么实现

### 1. 为什么要补 `ix_index_handle.cpp`

框架里已经有 `IxManager`、`IxIndexHandle`、`IxNodeHandle`、`IxScan` 等类，但很多核心函数是空的，例如：

```cpp
int IxNodeHandle::lower_bound(const char *target) const;
int IxNodeHandle::upper_bound(const char *target) const;
bool IxNodeHandle::leaf_lookup(const char *key, Rid **value);
page_id_t IxNodeHandle::internal_lookup(const char *key);
page_id_t IxIndexHandle::insert_entry(const char *key, const Rid &value, Transaction *transaction);
bool IxIndexHandle::get_value(const char *key, std::vector<Rid> *result, Transaction *transaction);
Iid IxIndexHandle::lower_bound(const char *key);
Iid IxIndexHandle::upper_bound(const char *key);
```

如果这些函数不实现，`create index` 即使创建了索引文件，也无法插入索引项，更无法通过索引查询。

### 2. 节点内二分查找

在 `src/index/ix_index_handle.cpp` 中实现：

```cpp
int IxNodeHandle::lower_bound(const char *target) const;
int IxNodeHandle::upper_bound(const char *target) const;
```

写法：

1. `lower_bound` 找第一个 `key >= target` 的位置。
2. `upper_bound` 找第一个 `key > target` 的位置。
3. 比较时调用框架已有的 `ix_compare`，因为索引 key 可能是多个字段拼接而成。

为什么这么写：

1. 点查需要 `lower_bound` 定位等值 key。
2. 范围查询需要用 `lower_bound/upper_bound` 得到扫描起止位置。
3. B+ 树内部节点向下查找也依赖边界定位。

### 3. 叶子节点查找

实现：

```cpp
bool IxNodeHandle::leaf_lookup(const char *key, Rid **value);
```

写法：

1. 先在叶子节点中 `lower_bound(key)`。
2. 如果该位置没有越界，并且 key 完全相等，就返回对应 rid。
3. 否则返回 false。

为什么这么写：

唯一索引中一个 key 只能对应一条记录，所以找到一个 rid 就够了。

### 4. 内部节点查找

实现：

```cpp
page_id_t IxNodeHandle::internal_lookup(const char *key);
```

写法：

1. 内部节点保存的是每个孩子子树的首 key。
2. 查找时使用 `upper_bound(key) - 1`，找到最后一个小于等于目标 key 的分隔项。
3. 该分隔项对应的 rid.page_no 就是下一层孩子页号。

为什么这么写：

本框架的内部节点不是传统教材里“n 个 key、n+1 个孩子”的形式，而是每个 key 和一个孩子页号配对。每个 key 表示该孩子子树中的最小 key，所以要找最后一个不大于目标 key 的孩子。

### 5. 节点内插入和删除

实现：

```cpp
void IxNodeHandle::insert_pairs(int pos, const char *key, const Rid *rid, int n);
int IxNodeHandle::insert(const char *key, const Rid &value);
void IxNodeHandle::erase_pair(int pos);
int IxNodeHandle::remove(const char *key);
```

写法：

1. 插入时先移动 `[pos, size)` 的 key 和 rid，为新数据腾出位置。
2. 再把 key 和 rid 拷贝进去。
3. 删除时把后面的 key 和 rid 前移。
4. 插入前检查是否已有相同 key，唯一索引不能重复。

为什么 key 和 rid 要一起移动：

索引项本质是：

```text
key -> rid
```

如果只移动 key，不移动 rid，索引会把 key 指向错误的记录。

### 6. 查找叶子页

实现：

```cpp
std::pair<IxNodeHandle *, bool> IxIndexHandle::find_leaf_page(...);
```

写法：

1. 从根节点开始。
2. 如果当前节点不是叶子节点，就调用 `internal_lookup` 找下一层孩子。
3. 一直向下直到叶子节点。
4. 返回叶子节点句柄。

为什么这么写：

B+ 树所有真实数据项都在叶子节点里，内部节点只负责导航。

### 7. 点查

实现：

```cpp
bool IxIndexHandle::get_value(const char *key, std::vector<Rid> *result, Transaction *transaction);
```

写法：

1. 调用 `find_leaf_page` 找到 key 应该所在的叶子页。
2. 调用 `leaf_lookup`。
3. 如果找到，就把 rid 放入 result。
4. 用完页后 unpin。

为什么结果用 `vector<Rid>`：

框架接口已经这样设计。虽然本题是唯一索引，一个 key 最多一个 rid，但保持接口不变更安全。

### 8. 插入索引项

实现：

```cpp
page_id_t IxIndexHandle::insert_entry(const char *key, const Rid &value, Transaction *transaction);
```

写法：

1. 先调用 `get_value` 检查 key 是否已存在。
2. 如果存在，抛出唯一索引冲突错误。
3. 找到应该插入的叶子页。
4. 插入 key 和 rid。
5. 如果叶子页满了，就调用 `split` 分裂。
6. 分裂后把新节点的首 key 插入父节点。

为什么先检查唯一性：

本题索引是唯一索引。如果先把记录写入基表，再发现索引冲突，基表和索引就可能不一致。因此执行器层也会提前检查唯一性。

### 9. 分裂节点

实现：

```cpp
IxNodeHandle *IxIndexHandle::split(IxNodeHandle *node);
```

写法：

1. 创建一个新节点。
2. 把原节点右半部分 key/rid 移动到新节点。
3. 如果是叶子节点，维护叶子链表的 `prev_leaf` 和 `next_leaf`。
4. 如果是内部节点，更新被移动孩子的 parent。

为什么叶子链表重要：

范围查询不是只查一个 key，而是从 lower bound 开始一路扫到 upper bound。扫完一个叶子页后，需要通过 `next_leaf` 进入下一个叶子页。

### 10. 向父节点插入

实现：

```cpp
void IxIndexHandle::insert_into_parent(...);
```

写法：

1. 如果被分裂节点是根节点，就创建新根。
2. 新根包含两个孩子：旧节点和新节点。
3. 如果不是根节点，就把新节点的首 key 插入父节点。
4. 如果父节点也满了，继续分裂父节点。

为什么父节点保存新节点的首 key：

因为本实现内部节点的 key 表示孩子子树中的最小 key。新节点分裂出来后，它的第一个 key 就是父节点需要记录的分隔信息。

### 11. 删除索引项

实现：

```cpp
bool IxIndexHandle::delete_entry(const char *key, Transaction *transaction);
```

写法：

1. 找到 key 所在叶子页。
2. 删除对应 key/rid。
3. 如果删除的是叶子页第一个 key，需要调用 `maintain_parent` 更新父节点分隔 key。

为什么没有完整实现合并和重分配：

题目三重点是索引可用、查询加速和基表同步。删除后即使节点利用率下降，只要叶子链表和父节点分隔 key 仍可用，查询结果仍然正确。为了降低风险，本实现选择轻量删除策略，不强制做复杂的 B+ 树合并重平衡。

### 12. 范围边界

实现：

```cpp
Iid IxIndexHandle::lower_bound(const char *key);
Iid IxIndexHandle::upper_bound(const char *key);
```

写法：

1. 先找到 key 应该所在的叶子页。
2. 在叶子页内部调用节点级别的 `lower_bound/upper_bound`。
3. 如果位置刚好落在页尾，并且还有下一个叶子页，就跳到下一个叶子页开头。
4. 返回 `{page_no, slot_no}` 形式的索引游标位置。

为什么需要 `Iid`：

`IxScan` 需要从一个索引位置扫到另一个索引位置。`Iid` 就是索引内部的游标，包含叶子页号和槽位号。

## 四、IxScan 怎么改

文件：

```text
src/index/ix_scan.cpp
```

实现：

```cpp
void IxScan::next();
Rid IxScan::rid() const;
```

关键点：

1. `next()` 先让 slot 后移。
2. 如果当前叶子页扫完，并且不是最后一个叶子页，就跳到下一个叶子页。
3. 每次 fetch 节点后要 unpin，否则缓冲池 pin 计数会一直增加。
4. `rid()` 根据当前 `Iid` 返回索引项中的记录位置。

为什么要补 unpin：

如果范围查询很多，每次 `IxScan::next()` 都 fetch 页但不 unpin，缓冲池会逐渐没有可替换页，后续查询可能卡住或者失败。

## 五、IndexScanExecutor 怎么实现

文件：

```text
src/execution/executor_index_scan.h
```

### 1. 它负责什么

`IndexScanExecutor` 是查询执行层的索引扫描算子。

它做三件事：

1. 根据 where 条件生成索引扫描范围。
2. 调用 `IxScan` 扫描索引，拿到候选 rid。
3. 根据 rid 回表读取记录，并用完整 where 条件过滤。

### 2. 为什么还要完整过滤

例如联合索引 `(w_id, name)`，查询：

```sql
select * from warehouse where w_id < 600 and name > 'bztyhnmj';
```

按照最左匹配原则，索引只能有效使用第一列 `w_id < 600`。第二列 `name > 'bztyhnmj'` 不能继续缩小 B+ 树范围，但仍然必须参与结果过滤。

所以索引扫描流程是：

```text
先用 w_id < 600 找候选记录
再用完整条件 w_id < 600 and name > 'bztyhnmj' 过滤
```

这样既利用了索引，又保证结果正确。

### 3. 如何构造复合 key 的上下界

索引 key 是多个字段拼接而成，例如：

```text
(w_id, name)
```

在内存中是：

```text
w_id 的二进制值 + name 的定长字符串值
```

为了支持前缀匹配，需要构造低 key 和高 key。

对于等值条件：

```sql
w_id = 100
```

低 key 和高 key 都写入 `100`。

对于范围条件：

```sql
w_id > 100
```

低 key 写入 `100`，剩余列补最大值，然后用 `upper_bound`。这样可以排除所有 `w_id = 100` 的记录。

对于：

```sql
w_id >= 100
```

低 key 写入 `100`，剩余列补最小值，然后用 `lower_bound`。这样可以包含所有 `w_id = 100` 的记录。

对于：

```sql
w_id < 600
```

高 key 写入 `600`，剩余列补最大值，然后用 `lower_bound`。这样会排除所有 `w_id = 600` 的记录。

对于：

```sql
w_id <= 600
```

高 key 写入 `600`，剩余列补最大值，然后用 `upper_bound`。这样会包含所有 `w_id = 600` 的记录。

### 4. 不同类型怎么补最小值和最大值

在 `IndexScanExecutor` 中实现：

```cpp
fill_min(...)
fill_max(...)
```

规则：

1. `int` 最小值用 `std::numeric_limits<int>::min()`。
2. `int` 最大值用 `std::numeric_limits<int>::max()`。
3. `float` 最小值用 `std::numeric_limits<float>::lowest()`。
4. `float` 最大值用 `std::numeric_limits<float>::max()`。
5. `char(n)` 最小值用全 0。
6. `char(n)` 最大值用全 `0xff`。

为什么字符串最大值用 `0xff`：

字符串索引比较使用 `memcmp`，全 `0xff` 在字节序上大于普通 ASCII 字符，适合作为定长字符串上界填充值。

### 5. 为什么先物化候选 rid

`IndexScanExecutor::beginTuple()` 中会先把满足条件的 rid 收集到 `matched_rids_`。

这么做有两个好处：

1. select 时遍历更简单，`Next()` 只需要按 rid 回表。
2. delete/update 时不会出现一边扫索引、一边修改索引导致游标不稳定的问题。

## 六、优化器如何选择索引

文件：

```text
src/optimizer/planner.cpp
```

修改函数：

```cpp
bool Planner::get_index_cols(std::string tab_name,
                             std::vector<Condition> curr_conds,
                             std::vector<std::string>& index_col_names);
```

### 1. 原来的问题

原来的逻辑大致是：

```cpp
for cond in curr_conds:
    if cond 是等值条件:
        index_col_names.push_back(cond 的列名)

if tab.is_index(index_col_names):
    使用索引
```

这有三个问题：

1. 只支持等值查询。
2. 必须完全匹配索引列。
3. where 条件顺序会影响生成的列顺序。

例如：

```sql
create index A(id,name);
select * from A where name = 'aaa' and id = 1;
```

原逻辑可能生成 `(name,id)`，从而匹配不上 `(id,name)`。

### 2. 新的最左匹配规则

新的逻辑是遍历表上所有索引：

1. 从索引第一列开始。
2. 在 where 条件里查找该列是否有等值条件。
3. 如果有等值条件，匹配长度加一，继续下一列。
4. 如果没有等值条件，但有范围条件，匹配长度加一，然后停止。
5. 如果既没有等值也没有范围，停止。
6. 选择匹配长度最长的索引。

这样可以支持：

```sql
where id = 1
where id > 1
where id = 1 and name = 'aaa'
where name = 'aaa' and id = 1
where id = 1 and name > 'aaa'
```

### 3. 为什么返回完整索引列

即使查询只匹配了联合索引的第一列，也要返回完整索引列名，例如 `(id,name)`。

原因是索引文件名、索引元数据、复合 key 长度都依赖完整索引定义。执行器内部会根据条件决定实际用到多少前缀列。

## 七、创建索引怎么实现

文件：

```text
src/system/sm_manager.cpp
```

函数：

```cpp
void SmManager::create_index(const std::string& tab_name,
                             const std::vector<std::string>& col_names,
                             Context* context);
```

流程：

1. 检查表是否存在。
2. 检查同名同列索引是否已经存在。
3. 根据列名找到对应 `ColMeta`。
4. 调用 `IxManager::create_index` 创建索引文件。
5. 打开索引文件。
6. 扫描整张表。
7. 对每条记录拼接索引 key。
8. 检查 key 是否重复。
9. 插入索引项。
10. 把 `IndexMeta` 写入表元数据。
11. 把索引句柄放入 `ihs_`。
12. 刷新元数据。

为什么创建索引时要扫描整张表：

索引不是只服务未来插入的数据。建索引之前表中已经存在的记录也必须写入索引，否则建索引后查询旧数据会查不到。

为什么创建索引时要检查唯一性：

如果表中已经有重复 key，那么唯一索引不应该创建成功。否则索引无法表达“一 key 对一记录”的约束。

## 八、删除索引怎么实现

文件：


函数：

```cpp
void SmManager::drop_index(const std::string& tab_name,
                           const std::vector<std::string>& col_names,
                           Context* context);
```

流程：

1. 检查表是否存在。
2. 根据列名找到 `IndexMeta`。
3. 从 `ihs_` 中取出索引句柄并关闭。
4. 删除索引文件。
5. 从表元数据中删除该索引。

为什么先关闭再删除文件：

索引文件句柄还打开时直接删除可能失败，也可能导致缓冲池中还有未刷新的索引页。


在 `QlManager::run_cmd_utility` 中加入：

```cpp
case T_ShowIndex:
    sm_manager_->show_index(x->tab_name_, context);
    break;
```

在 `SmManager` 中新增：

```cpp
void SmManager::show_index(const std::string& tab_name, Context* context);
```

输出逻辑：

1. 读取表元数据。
2. 遍历 `tab.indexes`。
3. 拼出列名字符串，例如 `(id,name)`。
4. 写入 `output.txt`：

```text
| warehouse | unique | (id,name) |
```

为什么不输出表头：

题目给出的 `show index` 期待输出只有索引行，没有表头，所以这里直接输出记录行。

## 十、插入时如何维护索引

文件：

```text
src/execution/executor_insert.h
```

流程：

1. 根据表元数据把 values 拼成一条完整记录。
2. 对每个索引拼出 key。
3. 插入基表前，先调用 `ih->get_value` 检查 key 是否已存在。
4. 如果存在，抛出唯一索引冲突。
5. 所有索引都检查通过后，再插入基表。
6. 拿到新记录 rid。
7. 把每个 key 插入对应索引。

为什么要先检查索引再插入基表：

如果先插基表，后发现索引唯一性冲突，基表里就多了一条不该存在的记录。题目没有要求完整事务回滚，所以最稳妥的方式是在基表写入前完成唯一性检查。

## 十一、删除时如何维护索引

文件：

```text
src/execution/executor_delete.h
```

流程：

1. Portal 先通过扫描算子收集要删除的 rid。
2. DeleteExecutor 根据 rid 读取旧记录。
3. 对表上每个索引拼出旧 key。
4. 调用 `ih->delete_entry` 删除索引项。
5. 删除基表记录。

为什么要先删索引再删基表：

删除索引 key 需要旧记录内容。如果先删除基表，再想拼旧 key，就拿不到记录数据了。

## 十二、更新时如何维护索引

文件：

```text
src/execution/executor_update.h
```

流程：

1. 根据 rid 读取旧记录。
2. 复制旧记录形成新记录。
3. 根据 set 子句修改新记录。
4. 对每个索引分别拼旧 key 和新 key。
5. 如果旧 key 和新 key 不同，先检查新 key 是否已存在。
6. 删除旧索引项。
7. 插入新索引项。
8. 更新基表记录。

为什么要比较旧 key 和新 key：

如果更新的字段和某个索引无关，那么该索引 key 实际没变。即使重新删除再插入也能工作，但比较后可以避免不必要的唯一性误判和额外操作。

## 十三、元数据为什么要修改

文件：

```text
src/system/sm_meta.h
```

修改点：

```cpp
TabMeta(const TabMeta &other) {
    name = other.name;
    for(auto col : other.cols) cols.push_back(col);
    for(auto index : other.indexes) indexes.push_back(index);
}
```

为什么要复制 indexes：

执行器里经常会把 `TabMeta` 从 `db_.get_table()` 拷贝到成员变量中。如果拷贝构造函数只复制列信息、不复制索引信息，那么 `IndexScanExecutor` 里就拿不到索引元数据，会导致 `get_index_meta` 失败。

## 十四、索引文件头为什么要修正

文件：

```text
src/index/ix_defs.h
```

修改点：

1. 去掉 `deserialize` 中调试用的 `std::cout << col_num_`。
2. 保持索引文件头反序列化只读元数据，不污染 SQL 输出。

为什么要去掉输出：

题目测试看的是 `output.txt`，但服务端标准输出中多余内容也会干扰调试。索引文件打开时不应该打印内部字段数量。

## 十七、常见错误和本实现如何避免

### 1. 只建索引文件，不把已有记录写入索引

后果：

建索引后查询不到建索引前插入的数据。

解决：

`SmManager::create_index` 扫描整张表，把已有记录全部插入索引。

### 2. 联合索引必须完全匹配才使用

后果：

`where id = 1` 无法使用 `(id,name)` 索引。

解决：

`Planner::get_index_cols` 改成最左匹配。

### 3. where 条件顺序影响索引匹配

后果：

`where name='aaa' and id=1` 匹配不上 `(id,name)`。

解决：

优化器按索引列顺序主动在条件集合里查找对应列，不依赖 SQL 条件顺序。

### 4. 范围查询没有正确处理开闭区间

后果：

`>` 和 `>=`、`<` 和 `<=` 输出相同，边界记录错误。

解决：

`IndexScanExecutor` 根据操作符选择 `lower_bound` 或 `upper_bound`。

### 5. 删除或更新记录后索引仍指向旧 rid

后果：

索引查询查到已删除记录，或者查不到更新后的记录。

解决：

`DeleteExecutor` 删除索引项，`UpdateExecutor` 删除旧 key 并插入新 key。

### 6. 唯一索引没有检查重复 key

后果：

同一个 key 可能指向多条记录，唯一索引语义失效。

解决：

创建索引、插入记录、更新索引列时都调用 `get_value` 检查重复 key。

### 7. TabMeta 拷贝时丢失索引信息

后果：

执行器拿不到 `IndexMeta`，索引扫描失败。

解决：

修改 `TabMeta` 拷贝构造函数，复制 `indexes`。

## 十八、实现原则总结

题目三的核心不是单独实现一个 B+ 树，而是把 B+ 树接入整个数据库执行链路。

完整链路是：

```text
SQL
  -> Parser 识别 create/drop/show index
  -> Analyze 检查表和列
  -> Optimizer 根据最左匹配选择 IndexScan
  -> IndexScanExecutor 生成索引范围并回表过滤
  -> IxIndexHandle 执行 B+ 树查找、插入、范围定位
  -> Insert/Delete/Update 维护索引和基表一致
  -> SmManager 管理索引元数据和索引文件生命周期
```

只实现其中一段都不够。只有索引文件、优化器选择、执行器扫描、DML 维护四部分同时完成，题目三才能稳定通过。
